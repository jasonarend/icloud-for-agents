# Native Notes and Reminders development setup

Current implementation is a development increment with bounded reads and guarded change plans; full service support is still incomplete. Native Notes and Reminders are independently disabled by default. The shared helper routes the requested service before querying permission state; a Notes request does not query Reminders permissions, and unknown services are refused. Existing Mail/Calendar/Contacts configuration and approval modes are preserved.

**Current capabilities**

Reminders exposes OS permission status, source/list discovery, bounded task pages, daily and inclusive date-range queries, priority filters and exact reads through public EventKit. Structured public recurrence and alarm metadata is available; native tags, hierarchy, attachments and other advanced metadata remain incomplete. Approved changes cover list/task creation, list renaming with membership readback, selected task fields, completion/reopening and same-source moves. Recurring task edits remain gated on explicit occurrence/series handling.

Notes exposes account/folder discovery, bounded title pages, title/plaintext and exported table-text search, attachment metadata and unlocked text/HTML reads. Approved changes cover note and folder creation, supported-note appends, explicit complete title/body replacement and native-object moves between private folders in one source. Body rewrites refuse existing attachments, tables/checklists and unsupported exported structures. Appends must retain the original exported HTML as an exact prefix. Moves retain the native object rather than reconstructing its body or assets, and verify observable identity/content and source absence. Folder creation accepts an optional exact `parent_folder_id`; omitted means the selected account root. Nested creation binds the private parent and its ancestors, checks direct siblings for duplicate names, and verifies the returned folder’s physical parent. Nested creation has synthetic coverage and live exact-parent readback; the nested rich-note move round trip remains pending.

Both global and service access must be write-enabled. Strict local receipts remain the default; owner-selected trusted-client mode retains its existing authorization contract. Access-status tools report effective scope and policy without contacting Apple. Standing grants, general native-object edits and broader folder organization remain incomplete. Offset pages may shift during external edits; follow next_offset until done, including empty filtered pages.

**Owner-controlled setup**

An authorized agent can build the repository-owned helper with `scripts/build-native-helper.py`, using a new output directory for each reviewed build. Swift and codesign are macOS build-time tools; neither a separate MCP server nor an additional Python runtime dependency is required. The resulting app is ad-hoc signed for development. Notes transport validates the owned app directories, entrypoint, declared bundle identity and bundled fixed scripts; symlinked or group/world-writable assets are refused. Approval fingerprints include the executable, bundle metadata and scripts. A release still needs its own signing/distribution and upgrade-permission continuity evidence.

After the owner selects a service, private settings accept `native_services` alongside the optional `notes` and `reminders` service booleans. For example, these nonsecret fields illustrate the schema; they do not enable a live installation:

```json
{
  "native_services": {
    "notes": {"access_mode": "read-only", "source_ids": []},
    "reminders": {
      "access_mode": "read-only",
      "source_ids": [],
      "helper_path": "/absolute/path/to/iCloudAgentsHelper.app/Contents/MacOS/icloud-agents-native"
    }
  }
}
```

Empty source allowlists permit source metadata discovery only. Select exact returned IDs under owner authorization before listing containers or reading content. Do not infer native source identity from the configured IMAP login or account display name. The launcher never forwards inherited native opt-ins or native configuration.

The helper accepts protocol-versioned JSON on stdin. It includes fixed Notes and Reminders creation transports for the approved-plan executor; there is no arbitrary script or command action. Internal transport availability is not authorization to mutate data. Normal MCP reads cannot request a grant. An explicit local `request_access` helper action asks macOS for Reminders full access; the human handles the system dialog. That OS grant never enables application writes. Notes can optionally use the same helper path, which embeds the fixed JXA bridge and declares its Automation purpose. Helper status checks do not prompt; the explicit Notes permission action uses the normal macOS consent flow. The built-in osascript read route remains available when no Notes helper is configured. The helper launches as a normal macOS application for its own consent context, using an owner-private one-shot request/result directory under local Application Support, separately namespaced for each approval ledger. Moving the transport does not move or clear the ledger; retained requests from the previous transport remain visible. Error responses are retained for diagnosis and are never replayed automatically. Neither route resets or bypasses denied permissions. Permission-check timeouts are reported as unverified access, not as an empty account or a successful grant. Permission attribution depends on the launch host and must be validated per client. Do not reset privacy databases or bypass a denied prompt.

Opted-in services also expose `notes_prepare_os_access` / `notes_request_os_access` and their `reminders_` equivalents. The first tool creates a reviewed consent-request proposal; the second consumes it once under the existing strict-receipt or owner-selected trusted-client policy. The proposal describes the OS-level access, which is broader than the server's selected-source and read/write controls. The user handles the actual macOS dialog. A completed request reports granted, denied or unverified status separately and never selects sources or enables application writes. Timeouts do not trigger another prompt. Source selection and application-access elevation remain separate owner-controlled setup steps in this increment.

The agent handles supported setup steps; terminal commands remain an optional owner/operator path, consistent with existing services. Existing strict receipt and trusted-client workflows are not replaced by native OS permission grants.

**Validation status**

Offline tests cover independent service selection, stale-tool refusal, missing scope, disabled access, input bounds, fixed JSON dispatch, environment filtering and response failures. A compiled helper status check is native execution evidence only; full access, content reads and cross-device sync require their own live acceptance. Live development acceptance has exercised selected-source reads, dedicated test containers, rich and plain Notes, and representative Reminders. Live Notes creation has exposed title/body assignment and temporary-to-permanent identity transitions. Content readback confirms the body-only constructor saved its fixture, and synthetic regression tests cover unrelated draft transitions and ambiguous candidates; fresh real stdio creation now passes prepare, execution, independent readback, status and replay refusal for both services. A real stdio read-only fixture workflow also verifies table-text search and reminder range/priority queries with public metadata; ordinary creation proposals remain refused in read-only mode. Real stdio append/replacement tests also pass, including refusal to rewrite an existing native table. A basic-format fixture retains its original HTML prefix, bold, italic and link through append. A native-object move fixture also preserves the same note ID, exact HTML/table, creation date and exposed attachment identities in both directions, with source absence verified. Folder checks include private ancestors; queries and exact reads bind the note's actual container. Native objects may have a null filename, which is reported without inventing a file name. These readback checks are not a claim of full native-object or visual fidelity. Live development tests also cover reminder field edits, completion/reopening, due-date clearing and same-source moves. EventKit can synthesize a start date during a due-date change; updates explicitly preserve the reviewed start value. A single known-ID reminder update with failed readback can receive a separately approved correction proposal. Both original and corrective audits remain immutable, and independent readback must verify the original requested state before admission resumes. This route cannot retry creations, unknown mutations, incomplete batches or recurring tasks. Uncertain single-note creations with no returned ID have a separate explicit recovery proposal. An authorized client can accept one fully matching observed note or repair an exact title-only candidate using the original request. Source, folder, title uniqueness, lock/share state, attachments, before snapshot and complete requested content are checked. Recovery follows the selected strict/trusted policy; trusted-client review is not independent proof of human review. It records an association rather than claiming the provider returned that creation ID. Original failure records remain unchanged. A read-only finalize tool can complete an interrupted successful recovery proof. This is not a generic uncertainty clear or a creation retry. A fixed-helper refusal before mutation dispatch consumes the plan and reports `refused_without_dispatch`, with request-bound evidence and separate prior verified items. The refused item was not applied; a new reviewed plan is required after resolving the cause. Save errors, timeouts, missing responses and failures after mutation dispatch remain uncertain. Failed or uncertain plans are retained and never replayed automatically. Rich fixtures and write testing require read-only success in both services and the separate write-access approval gate. These checks do not establish full feature, client-host, notification-delivery or cross-device acceptance.

**One approved action from read-only access**

Use `notes_prepare_once` or `reminders_prepare_once` with the same exact change dictionaries as the ordinary proposal tool. Review the returned batch and execute its plan ID with the service’s `execute_approved` tool. The configured strict local receipt or trusted-client policy still applies. This path requires an enabled service, selected sources and OS access; it cannot enable a disabled service or select another source.

Temporary authority covers only the exact consumed batch. It exists around each individual dispatch and ends on success or failure, including when a captured execution context outlives the call. Settings and environment stay unchanged, and a restart does not leave an unrestricted write window. A saved unconsumed plan can resume within its expiry only if access, backend, source scope and approval policy still match. Each item rechecks current authority and content; replay and uncertain-outcome protections remain in force. Use the service’s `cancel_plan` tool to withdraw an unstarted change plan; cancellation persists across restarts and cannot recall an in-flight operation. One-time elevation has synthetic lifecycle and MCP stdio coverage under both approval policies. Live Reminders creation from read-only access also passes, including independent readback, unchanged owner settings, replay refusal and cancellation of a subsequent edit. Live Notes one-time creation from read-only access also passes.


**Ongoing and scenario permissions**

Use the service’s `prepare_grant` tool to propose a scenario scope, then `activate_grant` after review. Strict mode requires the exact independent receipt from `icloud-agents-approve`; owner-selected trusted-client mode uses the existing client authorization policy. The activation review explicitly grants future batches inside its rules without another per-batch receipt. Mail grants never authorize native services.

A scope contains `scenario`, `rules`, `max_batch`, `max_24h` and `expires`. The scenario is a human-readable reference, not a natural-language content filter. Each rule specifies one exact `operation`, `source_id`, `container_id`, allowed input `fields`, and `destinations`. Use an empty destination array for ordinary operations; moves require exact destination IDs. Current rules cover the service’s implemented ordinary operations only. Unsupported operations, permanent deletion, collaboration changes, invitations, lock/password changes, recording and external export are excluded.

For example, a Notes meeting-summary scenario can allow `create_note` with `title` and `body`, or `append_note` with `body`, in one exact private folder. A Reminders action-item scenario can allow `create_reminder` with `title`, `notes`, `priority` and `due` in one selected list. A create-folder rule selects its exact parent folder or account root; create-list selects its source root. Existing reminder actions bind the item’s physical list. Field authorization refers to supplied input fields; adapter-derived content and preservation checks remain visible in each immutable batch review.

`max_batch` is 1–20. Set `max_24h` and `expires` to JSON `null` when the owner selects no aggregate cap or no expiry. A numeric expiry is a Unix timestamp. Admitted items count conservatively against the rolling cap, including failed or uncertain items. Quota reservations survive interruption and are not silently refunded. Grants survive server restarts while the same owner, service modes, backend fingerprint, source selection, approval policy and container metadata remain valid. Use `prepare_grant_replacement` to review before/after scope, then `activate_grant` on the returned ID. Activation retires the exact prior grant before the new scope becomes active; its rolling quota history carries forward. A denied or stale replacement leaves the prior authority unchanged. Interrupted admitted replacement is inactive until its original proof is finalized; it never silently revives either scope.

Use `prepare_with_grant` with the grant ID and exact changes, then `execute_approved` with the returned plan ID. This never changes read-only settings or opens a general write window. It rechecks the active grant, source/container, operations, fields, bounds and native snapshots before admission and each dispatch. Replay and uncertain-outcome protection still apply. `grant_status` reads the saved scope and current activation context without refreshing provider containers. Its separate `write_admission` field reports unfinished native operations that block an otherwise active grant. `revoke_grant` immediately prevents new admissions and remaining batch dispatches; it cannot recall an already in-flight effect. An unstarted batch can also be cancelled with `cancel_plan`.

If activation was admitted but its completion record was interrupted, `finalize_grant` verifies that original admission and completes only the local audit. It does not mint a receipt, issue another OS request, or write native data. Revoking an interrupted activation leaves it inactive and allows its no-data lifecycle to settle.

Optional terminal parity is available through `icloud-agents-native-access --service notes` or `--service reminders`, with `prepare --scope-file FILE`, `replace GRANT_ID --scope-file FILE`, `activate GRANT_ID`, `finalize GRANT_ID`, `status GRANT_ID`, `revoke GRANT_ID`, and `changes GRANT_ID --changes-file FILE`. Use the same owner configuration as the MCP server. The agent-led MCP path covers the same operations; terminal commands are an operator choice.


**Notes transport and interrupted batches**

The helper uses a fresh OSA language instance with a fixed send handler. Every Apple event carries `kAEDoNotPromptForUserConsent`; macOS enforces current access on each event. Ordinary reads and writes no longer depend on the blocking Automation preflight API. Status sends a fixed application-version property event and requires an actual reply; it reads no note or account content. Only an explicitly approved OS-access request uses the prompting API. Content requests normally open the fixed Notes app in the background before launching the helper. Status does not launch Notes.

Events and helper execution have finite deadlines. One completed `-1712` read-only event timeout may repeat once after source, service, mode and helper-fingerprint revalidation. The result reports `read_retry_count`. Permission denials, missing responses, consent requests and all mutations never repeat automatically. Exact-folder reads validate the target’s physical ancestry instead of walking the entire account. A timeout remains a real failure when those bounded steps cannot complete; it is never reported as empty content or successful permission.

A batch that stops during a read or authority check before its next native dispatch reports `stopped_before_dispatch`, with exact durable attempt records for any earlier verified items. Its plan stays consumed. For older failure records with a proven pre-dispatch phase, `finalize_stopped_plan` verifies the stored phase, plan hash and full completed-attempt prefix, then records a separate local finalization. The original failure stays unchanged. Mutation/verification failures, missing attempts, later dispatch evidence and unknown native effects cannot use this path. Resolving the read failure requires a new scoped batch; no write is replayed or rolled back automatically.


**Rename a Reminders list**

Prepare `rename_list` with an exact `source_id`, `list_id` and `fields: {"title": "New title"}`. The same ordinary, one-time or explicitly scoped standing-grant approval paths apply. The plan binds the writable list, sibling names and a complete bounded fingerprint of reminder IDs. Execution rechecks these before saving, then verifies the same list ID, source, writability and membership after the title change. Duplicate names, observed concurrent changes and read-only lists are refused. This changes no task content or completion state. The title can sync to existing devices or participants; EventKit does not expose participant state. Synthetic tests and a live round trip on a dedicated test list pass: its original name is restored, list identity and exact task membership are unchanged, and application access remains read-only.


The Notes helper’s watchdog shares a locked dispatch gate with the fixed JXA mutation code. Every constructor, insertion, body setter and move enters that gate immediately before the native primitive. A deadline closes the gate so later primitives cannot begin. A deadline before any entry returns a request-bound no-dispatch refusal; a deadline after entry remains uncertain. This distinction does not retroactively resolve older helper failures that lacked the gate.


**Observe one uncertain known-object move**

`notes_prepare_move_recovery` proposes accepting the current state of one exact pre-existing note ID after an uncertain single-note move. It requires the unchanged observable content and attachment identities in exactly one of the original source/destination folders, unshared physical ancestry, and a terminal helper response bound to the original request. Missing responses, ambiguous exchanges, missing/duplicated objects, changed content, other owners/sources and other operation kinds are refused.

`notes_accept_move_recovery` consumes that review under the configured strict-receipt or trusted-client policy. It records the observed source/destination location and explicitly leaves causal dispatch timing unproven. It does not move, recreate, edit or retry anything, and it preserves the original failed result. The old plan stays consumed. A successful association is a reviewed admission decision based on current verified state, not a claim that the original native operation succeeded or never ran. Later actions still use fresh snapshots and permissions.

`notes_finalize_move_recovery` completes a successful observation’s interrupted local proof. `notes_abandon_move_recovery` withdraws an unfinalized observation without clearing the original uncertainty or touching native data. A stale unconsumed observation can be replaced with a fresh review. New ordinary Notes dispatches also bind the helper request ID, request fingerprint and backend fingerprint to their immutable admitted plan before launch; identical payloads from separate attempts remain distinguishable. Older records require one unambiguous exact-request match and cannot borrow a missing response or a different attempt’s evidence.
