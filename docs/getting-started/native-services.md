# Native Notes and Reminders development setup

For a concise workflow overview, see [Notes and Reminders support](../reference/native-support.md).

Current implementation is a development increment with bounded reads and guarded change plans; full service support is still incomplete. Native Notes and Reminders are independently disabled by default. The shared helper routes the requested service before querying permission state; a Notes request does not query Reminders permissions, and unknown services are refused. Existing Mail/Calendar/Contacts configuration and approval modes are preserved.

**Current capabilities**

The existing `notes_access_status` and `reminders_access_status` tools report implementation boundaries through `unavailable_write_operations`. Unavailable operations are listed with reasons. `provider_capabilities: "not_probed"` and `operation_listing_is_authorization: false` distinguish this local implementation inventory from OS consent, a verified provider capability or permission to execute a change. Read-only status does not contact either app.

Reminders exposes OS permission status, source/list discovery, bounded task pages, daily and inclusive date-range queries, priority filters and exact reads through public EventKit. Structured public recurrence and alarm metadata is available; native tags, hierarchy, attachments and other advanced metadata remain incomplete. Approved changes cover list/task creation, list renaming and explicit sRGB list colors with membership readback, selected task fields and completion/reopening. With the explicitly selected ReminderKit backend, bounded same-source root moves keep every reviewed descendant together; the default EventKit backend refuses moves. Recurring task edits remain gated on explicit occurrence/series handling.

`reminders_query` also accepts `created_from`, `created_before`, `modified_from` and `modified_before` as UTC timestamps, with inclusive lower and exclusive upper bounds. Each filter excludes reminders whose corresponding timestamp is unavailable and reports that exclusion. Follow live-offset pages; concurrent changes can shift them. This is a bounded view of existing items, not a change log, deletion detector or proof of complete synchronization.

`reminders_export_page` returns a versioned JSON observation of one requested list within selected sources, up to 20 reminders and one million encoded bytes per page. Follow `next_offset` until `done`; list changes can shift pages, and an empty page does not establish that the requested list exists. It includes public fields and per-item coverage, and explicitly omits native tags, hierarchy, attachments and advanced metadata. It does not write a file or change Reminders. This is not an atomic backup or a restorable export; identifiers and public recurrence or alarm observations may be incomplete. A local read-only check found the dedicated synthetic fixture; real MCP transport and bounds have synthetic coverage.

`reminders_prepare_observation_copy` turns up to ten items from a supplied observation page into a reviewed proposal to create copies in one exact selected list. The caller must explicitly accept the omissions; copying due/start dates and URLs is individually optional. Every new reminder starts incomplete. Original identifiers, completion state, native tags, hierarchy, attachments, recurrence, alarms, location, sharing and timestamps are not copied. The supplied observation may be stale or incomplete, and copies may duplicate existing reminders. Date copying refuses unsupported or subminute times. Use ordinary one-time approval, or supply an active grant explicitly scoped to `copy_observation`; a generic `create_reminder` grant cannot be passed to this tool. A generic creation grant still allows its approved fields to be filled from caller-provided content through the ordinary creation tools. Scenario-grant limits, expiry and revocation apply. Source checks, unfinished-write guard, verification and no-replay behavior still apply. The proposal binds its limitations and options into the approval digest; it is not a restore. Synthetic approval and transport tests pass. Local one-time and explicitly scoped copy creation passed on dedicated synthetic fixtures; the test grants were revoked. Native metadata and cross-device fidelity remain unverified.

`reminders_export_ical` returns a single read-only [iCalendar VTODO](https://www.rfc-editor.org/rfc/rfc5545.html) with title, notes, completion, priority, supported URLs and location text, and supported date-only or zoned start/due values. Available creation, modification and completion timestamps are included to whole-second precision; unavailable timestamps and fractional seconds are omitted. Unambiguous zoned times are converted to UTC, without retaining the original timezone label. Supported absolute display alarms are included with text generated from the reminder title; importing can schedule notifications. It refuses ambiguous or nonexistent local times, unsupported URLs, relative or location alarms, recurrence, incomplete public metadata and mixed date types rather than guessing. The result reports omitted fields, including native tags, attachments, hierarchy and collaboration metadata. Its generated UID is pseudonymous; the output is not a complete or restorable backup. MCP transport, timezone, absolute-alarm and encoding cases have synthetic coverage; a dedicated local reminder without alarms also exported and parsed in a read-only check.

`reminders_prepare_ical_copy` accepts a bounded, CRLF-delimited iCalendar object containing one VTODO with explicit UID, timestamp, summary, status and supported priority. It accepts date-only or whole-minute UTC start/due values and up to ten absolute display alarms in 2000–2099; it refuses recurrence, relative or other alarm types, other components, unknown properties and unsupported parameters. It prepares a lossy copy: the caller explicitly accepts omissions and can select whether to copy dates, URLs and supported alarms. Copied alarms may schedule notifications and their display text may change; completed tasks become incomplete copies and location and timestamps are omitted. The original iCalendar digest and those effects are bound to the proposal. Use one-time approval or an explicitly scoped `copy_observation` grant that includes any selected alarm field. Synthetic tests cover the parser, alarms and MCP authorization paths. A local one-time copy without alarms passed creation and readback in a dedicated test list. Live copying of alarms and grant-backed iCalendar copies remain unverified.

`reminders_default_list` reads the system default through EventKit. It returns list details only when the list belongs to a selected source; an unselected default is reported without revealing its identity. No default or an older helper without this operation is reported separately. A local read matched the selected default against the list inventory; this does not change the system default or enable writes.

With the optional ReminderKit backend, `reminders_list_features` reads the provider’s grocery-categorization, shopping-session, group and sharing flags for one exact selected list. These observations do not identify every native list type or expose grocery categories, participants or permissions, and do not change the list. The shared-list case has synthetic coverage; a live shared list has not yet been verified. These flags require the updated native helper. With `include_pinned: true`, the same exact-list read also reports the native pin flag; the default response does not request it. This does not change pin state or establish list ordering. Synthetic tests cover pinned and unpinned flags, and a dedicated unpinned list passed live readback; dedicated pinned and unpinned list states have since passed the approved pin/unpin round trips described below. The opt-in pin observation requires the newer helper. Section, subtree-move, recovery, pin and badge plans bind these observed flags; other write plans do not yet bind them, and sharing may change after a read. Unsupported native interfaces refuse the read.

With the optional ReminderKit backend, `reminders_list_sections` reads up to 100 ordinary native section IDs and titles for one exact selected list. The helper verifies each section's account and list identity and sorts results by ID; this is not the app's display order. `reminders_get` can separately request `include_native_section` for one reminder. A reported section is verified against the selected account and list; `provider_not_reported` means the relationship is unknown, not that the reminder has no section. Unsupported native interfaces or inconsistent identities refuse the read. `create_section` accepts an exact source, list and title through the ordinary approval, one-time and scoped-grant paths. Section writes refuse when the provider reports grocery categorization, a grocery shopping session or a list group, and bind the observed flags before dispatch. Those flags do not prove the complete list type, so behavior on special lists remains unverified. It preassigns an ID and checks the observed section inventory and list reminder membership before and after saving; order and complete section membership remain unverified. Synthetic strict/trusted-client MCP tests and local one-time and scoped-grant creation tests passed with dedicated fixtures. `rename_section` targets one exact section ID and preserves the observed list inventory and reminder membership; scenario grants must explicitly name each section ID. Its fixed native method and closed dispatch gate have been tested, along with synthetic MCP approval paths, and a local rename passed independent readback in a dedicated synthetic list. Moving or deleting sections is not yet supported.

With the explicitly selected ReminderKit backend, `reminders_list_parent` observes the provider-reported parent group of one selected list. A returned group must match the same source and the list’s native parent identity; an unreported parent is not proof of a complete hierarchy. `reminders_group_lists` can separately observe bounded pages of provider-reported child lists in one exact selected-source group, checking each child account and parent identity and reporting the provider’s group flag for each child. It accepts up to 1,000 reported children and pages may shift when the group changes; follow `next_offset`. `reminders_inspect_group_hierarchy` follows these provider-reported group edges with explicit node and depth limits, rejecting repeated or cyclic IDs. Its separate reads can drift and it reports unexpanded groups. None of these observations proves complete hierarchy, membership or order, and none enables moving lists. Synthetic populated, foreign-account and inconsistent-state cases pass. A local ordinary list was refused as a group; the guarded grouping/ungrouping round trips below also verify populated native parent and child views. An updated helper is required.

With the explicitly selected ReminderKit backend, `reminders_smart_lists` lists bounded custom Smart List IDs and titles in one selected source. The helper checks account and record identities, refuses unknown or oversized provider collections, and sorts pages by ID; the pages may shift as lists change. This does not include built-in views, filter rules or matching reminders, and does not create or modify lists. Synthetic populated and scope-refusal tests pass, and a dedicated native-UI custom view passed local populated discovery and definition reads. An updated helper is required.

With the explicitly selected ReminderKit backend, `reminders_templates` lists bounded native template IDs and titles for one selected source. It verifies each template belongs to that account and refuses unknown provider shapes, duplicate identities or inventories over 1,000 records. Pages are sorted by ID and can shift if templates change. `reminders_template_sections` can inspect bounded provider-reported section IDs and titles on one exact template; account and parent identities are verified, while complete section coverage, display order and reminder membership are not. The listing does not expose template reminder contents or sharing links and does not create, edit, instantiate or delete templates. Synthetic scope, populated-section and pagination tests pass; two pages of existing templates and an empty section observation were read locally without changes. A populated template section has not been verified live. An updated helper is required.

With the explicitly selected ReminderKit backend, `reminders_get` accepts `include_native_assignment: true` for one exact reminder. It reports whether the provider returned a current assignment and the count of assignment records, without exposing identities or inferring the assignee, permissions, notifications or completeness. Unsupported or inconsistent provider data is refused. Synthetic tests cover present, absent and inconsistent observations; a dedicated unassigned reminder passed a local live read. `reminders_query` and `reminders_daily` can filter on `has_current_assignment` using that same provider observation, with bounded pages and the usual continuation behavior. This is not an “assigned to me” filter. Synthetic true and false cases and a local unassigned fixture query passed. A live assigned reminder and assignment changes have not been verified. An updated helper is required.

With the explicitly selected ReminderKit backend, `reminders_get` accepts `include_native_attachments: true` to inspect up to 100 native attachment records for one exact reminder. It returns scoped record IDs, observed native kinds and optional type identifiers; it does not return file paths, URLs or content. Unknown record types, inconsistent identities and oversized collections are refused. The observation does not establish that all attachment representations are covered. `reminders_query` and `reminders_daily` can filter `has_native_attachments` by whether the provider returned any of these records; an empty observation is not proof that every possible representation is absent. Follow bounded pages to completion. Synthetic populated and refusal cases pass; local live checks covered empty collections and a no-attachments query only. Exporting, adding or removing reminder attachments is not supported by this read. An updated helper is required.

An optional `reminders_get` request with `include_native_early` reads the selected reminder's separate native early-reminder offsets. It reports the observed native values and a separate interpreted offset, not delivery guarantees; on the locally tested macOS version, units 0, 1 and 2 were observed as minutes, hours and days respectively; the native interval model identifies units 3 and 4 as weeks and months. Negative counts indicate before the due date. Other units are not interpreted; these are distinct from EventKit time alarms. The helper checks the account and reminder identity and refuses unavailable or malformed provider data. An empty observed payload means no early offset was reported by the provider at that read. `add_early` creates one offset in minutes, hours, days, weeks, or months on an incomplete or completed timed reminder only when the provider reports an empty early-alert state; its one-time proposal and scoped scenario grants explicitly review notification effects. Independent readback checks the offset and observed native metadata. Minute and hour creation passed local live tests; week and month creation have synthetic coverage only. Changing its timed due date reviews the resulting early-notification reschedule. Removing the timed due date is refused while an early reminder is observed; use a separately approved `clear_early` operation first. It takes exactly `fields: {"clear": true}` and removes one observed existing early offset, binding the complete provider payload fingerprint and native alert UUID. Due date, ordinary alarms, content and other observed native metadata must remain unchanged. One-time approval and exact-list scenario grants selecting `clear_early` and field `clear` use the same checks. A closed dispatch gate, changed fingerprint, multiple alerts or unsupported native metadata refuses the save. Updating an offset uses a reviewed clear followed by a fresh reviewed add; those are separate operations, so a later failure is reported as partial success without automatic replay or rollback. Live one-time and scenario-grant removal passed on a fresh future-dated fixture; the grant was revoked, and the original historical failed experiment remains preserved and unreplayed.


Notes exposes account/folder discovery, bounded title pages, title/plaintext and exported table-text search, attachment metadata and unlocked text/HTML reads, with an optional bounded Markdown view and explicit conversion-loss metadata. Approved changes cover note and folder creation, supported-note appends and prepends, exact literal text replacements, and explicit complete title/body replacement. The default scripting-only configuration limits content writes and nested-folder creation to the account's default creation folder. With the explicitly selected read-only metadata backend, the normal Notes writer also supports verified ordinary folders and their private ancestors. The optional native-model route remains a separate backend. Notes moves require the explicitly selected `notes-store-readonly` metadata backend, existing host permission to read the fixed folder metadata and an updated helper. Source, destination and their ancestors must have verified ordinary, nondeleted, nonsmart roles and remain unshared in the same selected account. The executor refreshes the snapshot before dispatch; the helper checks the bound folder identities, titles, parent relationships, sharing, note content and attachment inventory before moving the existing object. Readback checks native identity, observable content, attachments, roles, source absence and the independently read saved physical folder. Scripting-only location changes cannot report success. These separate reads are not an atomic provider transaction. The default scripting-only configuration refuses moves. Ordinary moves exclude special folders. Recoverable removal and restoration have their own system-folder checks, described below. Body rewrites refuse existing attachments, tables/checklists and unsupported exported structures. Appends must retain the original exported HTML as an exact prefix. Earlier ordinary-folder move tests retained native identity and observable content, but a later synthetic test showed that the same move route also accepts Recently Deleted as a destination. New move proposals therefore require the explicit metadata role checks; old proposals without them remain inadmissible. Folder creation accepts an optional exact `parent_folder_id`; omitted means the selected account root. Nested creation binds the private parent and its ancestors, checks direct siblings for duplicate names, and verifies the returned folder’s physical parent. A live table/link note round trip passed the current metadata guard with both one-time approval and an exact two-direction scenario grant. The original note identity, exported content and attachment identities were preserved; the test grant was revoked. These local observations do not establish every client’s permission behavior or cross-device fidelity.

`notes_export_observation` returns a versioned JSON observation of one exact scoped note using the ordinary Notes read. It includes bounded HTML and plaintext for an unlocked note and reports truncation; for a locked note it returns only its scoped identity and unavailable-content status. Concurrent edits can affect the read. It does not unlock notes, fetch attachment content or write a file. Native objects, attachments and collaboration details are omitted, so this is not a complete backup or restorable export. A local read-only check passed on a dedicated unlocked fixture; locked-note handling and MCP transport have synthetic coverage.

`notes_format_list_markdown` converts a bounded subset of plain headings, single-line paragraphs and nested unordered or consecutive numbered lists into HTML. It reads no Notes data and makes no change; pass its HTML to a separately reviewed Notes creation or edit with `format: "html"`. It refuses inline Markdown, links, tables, code blocks, checklists, unsupported indentation and nonconsecutive numbering rather than guessing. Its lists are HTML formatting, not native Notes checklist items, and formatting round trips are not guaranteed. The conversion and approval flow have synthetic coverage. Local creation preserved the observed nested list-container and item structure. Notes normalizes item containment in its HTML export; the Markdown view preserves nesting for that shape. Native checklist semantics, visual styles and cross-device behavior remain unverified.

`notes_inspect_exported_links` observes link elements in the bounded HTML export of one exact selected note, in pages of at most 50. Link labels and targets are untrusted note content, including potentially unsafe schemes; the tool does not open, resolve or verify them. It omits invalid or oversized targets, reports source truncation, and can check `expected_modified` on later pages. Locked notes return unavailable content rather than an empty link list. `html_links_complete` is false for unfinished link markup or a truncated export; it does not establish native-link completeness. Notes can change during or between reads, and native links inside objects, link identity and backlinks remain unverified. Synthetic tests cover paging, scope, lock handling and MCP transport; a link in a dedicated live fixture matched its exported HTML in a read-only check.

`notes_format_plain_table` converts bounded rows of single-line plain text cells into escaped HTML for a separately approved Notes creation or edit. Rows must have equal width; merged cells, native table identity and round-trip fidelity are not represented. This formatter does not read or write Notes. Synthetic tests cover escaping, bounds, MCP transport and the existing content validator. Local creation and exported table/link readback passed on a dedicated fixture; visual rendering and cross-device synchronization remain unverified.

`notes_find_html_references` looks for one exact decoded link target in the bounded HTML exports of up to three notes from one selected physical-folder page. It returns only matching note identities and titles, plus locked, truncated, unfinished-link or unavailable observations. It never opens the target. On a read failure it stops without retrying or silently skipping the failed note; restart the scan after resolving the failure. Follow folder pages when available, but do not treat the result as complete native backlinks: notes can change between reads, and native objects, other folders and unavailable content may contain additional references. Synthetic tests cover scope, matching, incomplete observations and failure handling.

`notes_prepare_observation_copy` accepts one supplied unlocked, nontruncated observation and prepares a reviewed copy into one exact selected folder. It requires explicit acceptance of omissions and a verifiable title/body boundary; unsupported HTML is refused by the ordinary Notes creation adapter. The original identity, native objects, attachments, collaboration, sharing and timestamps are not preserved, and formatting may change. The observation is user-supplied and may be stale, and a copy may duplicate an existing note. Use ordinary one-time approval, or an active grant explicitly scoped to `copy_observation`; a generic `create_note` grant cannot be passed to this tool. A generic creation grant still allows its approved fields to be filled from caller-provided content through the ordinary creation tools. Scenario-grant limits, expiry and revocation apply. Folder-role, source, unfinished-write and verification checks remain in force; this is not a restore. Synthetic tests cover both authorization paths. Supported dedicated fixtures passed local one-time and explicitly scoped copy creation and readback; the test grants were revoked. A rich fixture was refused. Full native object fidelity and cross-device behavior remain unverified.

For `notes_search`, `match_scope: "plaintext"` searches titles and bounded plaintext without separately fetching exported HTML for table text. This can reduce work on a slow search but can miss text available only in a table projection; the result states that limitation. `match_scope: "title"` avoids body reads altogether, and the default `all` retains the separate bounded table-text search. None of these modes guarantees that a stalled Notes app or a particular note will respond.

`notes_default_folder` reads the default folder of one exact selected Notes account. The result includes the folder identity, parent, title and sharing status; it does not change the default, grant access or establish roles for other folders. The fixed scripting bridge and a local selected-account read were checked independently.

Ordinary change preparation requires both global and service access to be write-enabled. Exact one-time plans and separately activated standing grants also work from read-only access, as described below. Strict local receipts remain the default; owner-selected trusted-client mode retains its existing authorization contract. Access-status tools report effective scope and policy without contacting Apple. General native-object edits and broader folder organization remain incomplete. Offset pages may shift during external edits; follow next_offset until done, including empty filtered pages.

**Notes permission identity**

The bundled helper is part of iCloud for Agents; the assistant builds and configures it during setup. The person choosing Notes approves the normal macOS Automation request. They do not need to configure a separate product or run a command. This standard path does not select the optional native Notes-store backend or request Full Disk Access.

`notes_status` reports the running process's `requester_identity` when a current helper is configured: its bundle identifier, declared bundle name, process name and launch mode. A reviewed OS-access request also records this identity when the helper supplies it. `dialog_attribution: "not_verified"` is intentional: these fields describe the process reporting them, not the name macOS actually displayed in a consent dialog. An older helper may omit the diagnostic; its omission does not grant permission. Status never requests consent or reads Notes content, and a stopped Notes app, denial or timeout remains a distinct result. If macOS reports a launcher failure after a valid private status response has arrived, `transport_warning: "launcher_nonzero_result_received"` preserves that distinction. This handling is limited to nonprompting status checks; it does not accept a failed launch for a content read, permission request or write.

The default development bundle is named `iCloud for Agents.app`, and declares `iCloud for Agents` as its bundle and display name. Existing installations keep their current helper path; setup never relocates or replaces them silently. macOS decides which name to display, so these metadata values are not proof of a prompt label. On one existing Mac, System Settings showed the previously built `iCloudAgentsHelper` entry with Notes enabled. A non-prompting comparison there returned granted for an application launch and denied for the direct executable, even though both reported the same bundle identifier. Use the configured app-launch transport for Notes; do not treat a direct process test as evidence for the app route. A local synthetic MCP client also passed a non-prompting status and exact dedicated-note read through the production stdio server and renamed helper. That does not establish acceptance for a named client.

Acceptance of a client requires observing the real consent dialog, the requesting app in Automation settings and a scoped Notes read through that same client and helper. Record the client version, macOS version, helper build/signature, launch route and outcome without note content. A process identity, already-granted status, ad-hoc signature or synthetic stdio test alone does not prove prompt attribution or upgrade continuity. The current development helper is ad-hoc signed; stable production signing, first-use prompts across clients and permission continuity after updates remain to be verified.

**Owner-controlled setup**

An authorized agent can build the repository-owned helper with `scripts/build-native-helper.py`, using a new output directory for each reviewed build. Swift and codesign are macOS build-time tools; neither a separate MCP server nor an additional Python runtime dependency is required. The resulting app is ad-hoc signed for development. Notes transport validates the owned app directories, entrypoint, declared bundle identity and bundled fixed scripts; symlinked or group/world-writable assets are refused. Approval fingerprints include the executable, bundle metadata and scripts. A release still needs its own signing/distribution and upgrade-permission continuity evidence.

After the owner selects a service, private settings accept `native_services` alongside the optional `notes` and `reminders` service booleans. For example, these nonsecret fields illustrate the schema; they do not enable a live installation:

```json
{
  "native_services": {
    "notes": {"access_mode": "read-only", "source_ids": []},
    "reminders": {
      "access_mode": "read-only",
      "source_ids": [],
      "helper_path": "/absolute/path/to/iCloud for Agents.app/Contents/MacOS/icloud-agents-native"
    }
  }
}
```

For an existing installation, the assistant can use `scripts/configure-native.py` to review and apply a nonsecret service configuration update. The user does not need to run its commands. Select `--service notes` or `--service reminders`, the exact signed executable through `--helper`, and optional repeated `--source-id` values discovered from that service. An omitted source selection preserves existing IDs; a new profile starts with an empty allowlist. `--clear-sources` explicitly restores discovery-only scope.

The default invocation only prints a preview and digest. After owner authorization of that exact scope, repeat the options with `--apply-review <digest>`. The digest binds the installation, current settings, helper bytes and selected changes; it is a stale-input check, not a human approval receipt. The utility verifies the helper's code signature, preserves other services, credentials labels, runtime location and approval policy, and saves a private exact settings backup before replacement. Newly enabled services start read-only, including previously disabled profiles that stored a write-enabled mode. Existing enabled service modes are preserved rather than silently changed. No OS permission, native write or standing grant is activated by this edit.

The utility serializes cooperating setup edits and native execution, and refuses a change while the owner's admitted writes remain unfinished or uncertain. Files edited outside this utility do not share its lock; avoid concurrent private-settings edits. Configured clients/server processes must restart before the change takes effect; running processes retain their old configuration. Disabling is available through `--disable-service` without a helper or source arguments, including when the old helper is unavailable. Restart affected processes to complete that configuration change. OS access and write approvals remain separate steps. These controls apply to the shared server configuration used by both stdio and tunnel clients.

Empty source allowlists permit source metadata discovery only. Select exact returned IDs under owner authorization before listing containers or reading content. Do not infer native source identity from the configured IMAP login or account display name. The launcher never forwards inherited native opt-ins or native configuration.

The helper accepts protocol-versioned JSON on stdin. It includes fixed Notes and Reminders creation transports for the approved-plan executor; there is no arbitrary script or command action. Internal transport availability is not authorization to mutate data. Normal MCP reads cannot request a grant. An explicit local `request_access` helper action asks macOS for Reminders full access; the human handles the system dialog. That OS grant never enables application writes. Notes can optionally use the same helper path, which embeds the fixed JXA bridge and declares its Automation purpose. Helper status checks do not prompt; the explicit Notes permission action uses the normal macOS consent flow. The built-in osascript read route remains available when no Notes helper is configured. The helper launches as a normal macOS application for its own consent context, using an owner-private one-shot request/result directory under local Application Support, separately namespaced for each approval ledger. Moving the transport does not move or clear the ledger; retained requests from the previous transport remain visible. Error responses are retained for diagnosis and are never replayed automatically. The normal helper reuses an already-running Notes app without sending a separate reopen event. When Notes is not running, it requests one bounded background launch of the fixed system app; a failed launch stops the request. Status checks remain nonlaunching. Neither route resets or bypasses denied permissions. Permission-check timeouts are reported as unverified access, not as an empty account or a successful grant. Permission attribution depends on the launch host and must be validated per client. Do not reset privacy databases or bypass a denied prompt.

Opted-in services also expose `notes_prepare_os_access` / `notes_request_os_access` and their `reminders_` equivalents. The first tool creates a reviewed consent-request proposal; the second consumes it once under the existing strict-receipt or owner-selected trusted-client policy. The proposal describes the OS-level access, which is broader than the server's selected-source and read/write controls. The user handles the actual macOS dialog. A completed request reports granted, denied or unverified status separately and never selects sources or enables application writes. Timeouts do not trigger another prompt. Source selection and application-access elevation remain separate owner-controlled setup steps in this increment.

The agent handles supported setup steps; terminal commands remain an optional owner/operator path, consistent with existing services. Existing strict receipt and trusted-client workflows are not replaced by native OS permission grants.

**One approved action from read-only access**

Use `notes_prepare_once` or `reminders_prepare_once` with the same exact change dictionaries as the ordinary proposal tool.
