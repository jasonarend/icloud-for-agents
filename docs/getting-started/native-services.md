# Native Notes and Reminders development setup

Current implementation is a development increment with bounded reads and guarded change plans; full service support is still incomplete. Native Notes and Reminders are independently disabled by default. The shared helper routes the requested service before querying permission state; a Notes request does not query Reminders permissions, and unknown services are refused. Existing Mail/Calendar/Contacts configuration and approval modes are preserved.

**Current capabilities**

Reminders exposes OS permission status, source/list discovery, bounded task pages, daily and inclusive date-range queries, priority filters and exact reads through public EventKit. Structured public recurrence and alarm metadata is available; native tags, hierarchy, attachments and other advanced metadata remain incomplete. Approved changes cover list/task creation, list renaming and explicit sRGB list colors with membership readback, selected task fields and completion/reopening. Same-source moves are paused until their complete hierarchy effects can be verified before dispatch. Recurring task edits remain gated on explicit occurrence/series handling.

Notes exposes account/folder discovery, bounded title pages, title/plaintext and exported table-text search, attachment metadata and unlocked text/HTML reads, with an optional bounded Markdown view and explicit conversion-loss metadata. Approved changes cover note and folder creation, supported-note appends and prepends, exact literal text replacements, explicit complete title/body replacement and native-object moves between private folders in one source. Body rewrites refuse existing attachments, tables/checklists and unsupported exported structures. Appends must retain the original exported HTML as an exact prefix. Moves retain the native object rather than reconstructing its body or assets, and verify observable identity/content and source absence. Folder creation accepts an optional exact `parent_folder_id`; omitted means the selected account root. Nested creation binds the private parent and its ancestors, checks direct siblings for duplicate names, and verifies the returned folder’s physical parent. Nested creation has synthetic coverage and live exact-parent readback; a live rich-note round trip into the nested folder and back also passed, preserving the exposed native ID, exported HTML/table, attachment inventory and source absence.

Ordinary change preparation requires both global and service access to be write-enabled. Exact one-time plans and separately activated standing grants also work from read-only access, as described below. Strict local receipts remain the default; owner-selected trusted-client mode retains its existing authorization contract. Access-status tools report effective scope and policy without contacting Apple. General native-object edits and broader folder organization remain incomplete. Offset pages may shift during external edits; follow next_offset until done, including empty filtered pages.

**Notes permission identity**

The bundled helper is part of iCloud for Agents; the assistant builds and configures it during setup. The person choosing Notes approves the normal macOS Automation request. They do not need to configure a separate product or run a command. This standard path does not select the optional native Notes-store backend or request Full Disk Access.

`notes_status` reports the running process's `requester_identity` when a current helper is configured: its bundle identifier, declared bundle name, process name and launch mode. A reviewed OS-access request also records this identity when the helper supplies it. `dialog_attribution: "not_verified"` is intentional: these fields describe the process reporting them, not the name macOS actually displayed in a consent dialog. An older helper may omit the diagnostic; its omission does not grant permission. Status never requests consent or reads Notes content, and a stopped Notes app, denial or timeout remains a distinct result.

The default development bundle is named `iCloud for Agents.app`, and declares `iCloud for Agents` as its bundle and display name. Existing installations keep their current helper path; setup never relocates or replaces them silently. macOS decides which name to display, so these metadata values are not proof of a prompt label. On one existing Mac, System Settings showed the previously built `iCloudAgentsHelper` entry with Notes enabled. A non-prompting comparison there returned granted for an application launch and denied for the direct executable, even though both reported the same bundle identifier. Use the configured app-launch transport for Notes; do not treat a direct process test as evidence for the app route. A local synthetic MCP client also passed a non-prompting status and exact dedicated-note read through the production stdio server and renamed helper. That does not establish acceptance for a named client.

Acceptance of a client requires observing the real consent dialog, the requesting app in Automation settings and a scoped Notes read through that same client and helper. Record the client version, macOS version, helper build/signature, launch route and outcome without note content. A process identity, already-granted status, ad-hoc signature or synthetic stdio test alone does not prove prompt attribution or upgrade continuity. The current development helper is ad-hoc signed; stable production signing, first-use prompts across clients and permission continuity after updates remain to be verified.

**Owner-controlled setup**

An authorized agent can build the repository-owned helper with `scripts/build-native-helper.py`, using a new output directory for each reviewed build. Swift and codesign are macOS build-time tools; neither a separate MCP server nor an additional Python runtime dependency is required. The resulting app is ad-hoc signed for development. Notes transport validates the owned app directories, entrypoint, declared bundle identity and bundled fixed scripts; symlinked or group/world-writable assets are refused. Approval fingerprints include the executable, bundle metadata and scripts. A release still needs its own signing/distribution and upgrade-permission continuity evidence.

After the owner selects a service, private settings accept `native_services` alongside the optional `notes` and `reminders` service booleans. For example, these nonsecret fields illustrate the schema; they do not enable a live installation:

```json
{
  "native_services": {
    "notes": {"access_mode": "read-only", "source_ids": []},
    "reminders": {
      "access_mode": "read-only",
      "source_ids": [],
      "helper_path": "/absolute/path/to/iCloud for Agents.app/Contents/MacOS/icloud-agents-native"
    }
  }
}
```

For an existing installation, the assistant can use `scripts/configure-native.py` to review and apply a nonsecret service configuration update. The user does not need to run its commands. Select `--service notes` or `--service reminders`, the exact signed executable through `--helper`, and optional repeated `--source-id` values discovered from that service. An omitted source selection preserves existing IDs; a new profile starts with an empty allowlist. `--clear-sources` explicitly restores discovery-only scope.

The default invocation only prints a preview and digest. After owner authorization of that exact scope, repeat the options with `--apply-review <digest>`. The digest binds the installation, current settings, helper bytes and selected changes; it is a stale-input check, not a human approval receipt. The utility verifies the helper's code signature, preserves other services, credentials labels, runtime location and approval policy, and saves a private exact settings backup before replacement. Newly enabled services start read-only, including previously disabled profiles that stored a write-enabled mode. Existing enabled service modes are preserved rather than silently changed. No OS permission, native write or standing grant is activated by this edit.

The utility serializes cooperating setup edits and native execution, and refuses a change while the owner's admitted writes remain unfinished or uncertain. Files edited outside this utility do not share its lock; avoid concurrent private-settings edits. Configured clients/server processes must restart before the change takes effect; running processes retain their old configuration. Disabling is available through `--disable-service` without a helper or source arguments, including when the old helper is unavailable. Restart affected processes to complete that configuration change. OS access and write approvals remain separate steps. These controls apply to the shared server configuration used by both stdio and tunnel clients.

Empty source allowlists permit source metadata discovery only. Select exact returned IDs under owner authorization before listing containers or reading content. Do not infer native source identity from the configured IMAP login or account display name. The launcher never forwards inherited native opt-ins or native configuration.

The helper accepts protocol-versioned JSON on stdin. It includes fixed Notes and Reminders creation transports for the approved-plan executor; there is no arbitrary script or command action. Internal transport availability is not authorization to mutate data. Normal MCP reads cannot request a grant. An explicit local `request_access` helper action asks macOS for Reminders full access; the human handles the system dialog. That OS grant never enables application writes. Notes can optionally use the same helper path, which embeds the fixed JXA bridge and declares its Automation purpose. Helper status checks do not prompt; the explicit Notes permission action uses the normal macOS consent flow. The built-in osascript read route remains available when no Notes helper is configured. The helper launches as a normal macOS application for its own consent context, using an owner-private one-shot request/result directory under local Application Support, separately namespaced for each approval ledger. Moving the transport does not move or clear the ledger; retained requests from the previous transport remain visible. Error responses are retained for diagnosis and are never replayed automatically. The normal helper reuses an already-running Notes app without sending a separate reopen event. When Notes is not running, it requests one bounded background launch of the fixed system app; a failed launch stops the request. Status checks remain nonlaunching. Neither route resets or bypasses denied permissions. Permission-check timeouts are reported as unverified access, not as an empty account or a successful grant. Permission attribution depends on the launch host and must be validated per client. Do not reset privacy databases or bypass a denied prompt.

Opted-in services also expose `notes_prepare_os_access` / `notes_request_os_access` and their `reminders_` equivalents. The first tool creates a reviewed consent-request proposal; the second consumes it once under the existing strict-receipt or owner-selected trusted-client policy. The proposal describes the OS-level access, which is broader than the server's selected-source and read/write controls. The user handles the actual macOS dialog. A completed request reports granted, denied or unverified status separately and never selects sources or enables application writes. Timeouts do not trigger another prompt. Source selection and application-access elevation remain separate owner-controlled setup steps in this increment.

The agent handles supported setup steps; terminal commands remain an optional owner/operator path, consistent with existing services. Existing strict receipt and trusted-client workflows are not replaced by native OS permission grants.

**Validation status**

Offline tests cover independent service selection, stale-tool refusal, missing scope, disabled access, input bounds, fixed JSON dispatch, environment filtering and response failures. A compiled helper status check is native execution evidence only; full access, content reads and cross-device sync require their own live acceptance. Live development acceptance has exercised selected-source reads, dedicated test containers, rich and plain Notes, and representative Reminders. Live Notes creation has exposed title/body assignment and temporary-to-permanent identity transitions. Content readback confirms the body-only constructor saved its fixture, and synthetic regression tests cover unrelated draft transitions and ambiguous candidates; fresh real stdio creation now passes prepare, execution, independent readback, status and replay refusal for both services. A real stdio read-only fixture workflow also verifies table-text search and reminder range/priority queries with public metadata; ordinary creation proposals remain refused in read-only mode. Real stdio append/replacement tests also pass, including refusal to rewrite an existing native table. A basic-format fixture retains its original HTML prefix, bold, italic and link through append. A native-object move fixture also preserves the same note ID, exact HTML/table, creation date and exposed attachment identities in both directions, with source absence verified. Folder checks include private ancestors; queries and exact reads bind the note's actual container. Native objects may have a null filename, which is reported without inventing a file name. These readback checks are not a claim of full native-object or visual fidelity. Live development tests also covered reminder field edits, completion/reopening, due-date clearing and same-source moves on dedicated fixtures; moves are now paused because those tests did not establish complete hierarchy safety. EventKit can synthesize a start date during a due-date change; updates explicitly preserve the reviewed start value. A single known-ID reminder update with failed readback can receive a separately approved correction proposal. Both original and corrective audits remain immutable, and independent readback must verify the original requested state before admission resumes. This route cannot retry creations, unknown mutations, incomplete batches or recurring tasks. Uncertain single-note creations with no returned ID have a separate explicit recovery proposal. An authorized client can accept one fully matching observed note or repair an exact title-only candidate using the original request. Source, folder, title uniqueness, lock/share state, attachments, before snapshot and complete requested content are checked. Recovery follows the selected strict/trusted policy; trusted-client review is not independent proof of human review. It records an association rather than claiming the provider returned that creation ID. Original failure records remain unchanged. A read-only finalize tool can complete an interrupted successful recovery proof. This is not a generic uncertainty clear or a creation retry. A fixed-helper refusal before mutation dispatch consumes the plan and reports `refused_without_dispatch`, with request-bound evidence and separate prior verified items. The refused item was not applied; a new reviewed plan is required after resolving the cause. Save errors, timeouts, missing responses and failures after mutation dispatch remain uncertain. Failed or uncertain plans are retained and never replayed automatically. Rich fixtures and write testing require read-only success in both services and the separate write-access approval gate. These checks do not establish full feature, client-host, notification-delivery or cross-device acceptance.

**One approved action from read-only access**

Use `notes_prepare_once` or `reminders_prepare_once` with the same exact change dictionaries as the ordinary proposal tool. Review the returned batch and execute its plan ID with the service’s `execute_approved` tool. The configured strict local receipt or trusted-client policy still applies. This path requires an enabled service, selected sources and OS access; it cannot enable a disabled service or select another source.

Temporary authority covers only the exact consumed batch. It exists around each individual dispatch and ends on success or failure, including when a captured execution context outlives the call. Settings and environment stay unchanged, and a restart does not leave an unrestricted write window. A saved unconsumed plan can resume within its expiry only if access, backend, source scope and approval policy still match. Each item rechecks current authority and content; replay and uncertain-outcome protections remain in force. Use the service’s `cancel_plan` tool to withdraw an unstarted change plan; cancellation persists across restarts and cannot recall an in-flight operation. One-time elevation has synthetic lifecycle and MCP stdio coverage under both approval policies. Live Reminders creation from read-only access also passes, including independent readback, unchanged owner settings, replay refusal and cancellation of a subsequent edit. Live Notes one-time creation from read-only access also passes.


**Ongoing and scenario permissions**

Use the service’s `prepare_grant` tool to propose a scenario scope, then `activate_grant` after review. Strict mode requires the exact independent receipt from `icloud-agents-approve`; owner-selected trusted-client mode uses the existing client authorization policy. The activation review explicitly grants future batches inside its rules without another per-batch receipt. Mail grants never authorize native services.

A scope contains `scenario`, `rules`, `max_batch`, `max_24h` and `expires`. The scenario is a human-readable reference, not a natural-language content filter. Each rule specifies one exact `operation`, `source_id`, `container_id`, allowed input `fields`, and `destinations`. Use an empty destination array for ordinary operations; moves require exact destination IDs. Current rules cover the service’s implemented ordinary operations only. Unsupported operations, permanent deletion, collaboration changes, invitations, lock/password changes, recording and external export are excluded.

For example, a Notes meeting-summary scenario can allow `create_note` with `title` and `body`, or `append_note` with `body`, in one exact private folder. A Reminders action-item scenario can allow `create_reminder` with `title`, `notes`, `priority` and `due` in one selected list. A create-folder rule selects its exact parent folder or account root; create-list selects its source root. Existing reminder actions bind the item’s physical list. Field authorization refers to supplied input fields; adapter-derived content and preservation checks remain visible in each immutable batch review.

`max_batch` is 1–20. Set `max_24h` and `expires` to JSON `null` when the owner selects no aggregate cap or no expiry. A numeric expiry is a Unix timestamp. Admitted items count conservatively against the rolling cap, including failed or uncertain items. Quota reservations survive interruption and are not silently refunded. Grants survive server restarts while the same owner, service modes, backend fingerprint, source selection, approval policy and container metadata remain valid. Use `prepare_grant_replacement` to review before/after scope, then `activate_grant` on the returned ID. Activation retires the exact prior grant before the new scope becomes active; its rolling quota history carries forward. A denied or stale replacement leaves the prior authority unchanged. Interrupted admitted replacement is inactive until its original proof is finalized; it never silently revives either scope.

Use `prepare_with_grant` with the grant ID and exact changes, then `execute_approved` with the returned plan ID. This never changes read-only settings or opens a general write window. It rechecks the active grant, source/container, operations, fields, bounds and native snapshots before admission and each dispatch. Replay and uncertain-outcome protection still apply. `grant_status` reads the saved scope and current activation context without refreshing provider containers. Its separate `write_admission` field reports unfinished native operations that block an otherwise active grant. `revoke_grant` immediately prevents new admissions and remaining batch dispatches; it cannot recall an already in-flight effect. An unstarted batch can also be cancelled with `cancel_plan`.

If activation was admitted but its completion record was interrupted, `finalize_grant` verifies that original admission and completes only the local audit. It does not mint a receipt, issue another OS request, or write native data. Revoking an interrupted activation leaves it inactive and allows its no-data lifecycle to settle.

Optional terminal parity is available through `icloud-agents-native-access --service notes` or `--service reminders`, with `prepare --scope-file FILE`, `replace GRANT_ID --scope-file FILE`, `activate GRANT_ID`, `finalize GRANT_ID`, `status GRANT_ID`, `revoke GRANT_ID`, and `changes GRANT_ID --changes-file FILE`. Use the same owner configuration as the MCP server. The agent-led MCP path covers the same operations; terminal commands are an operator choice.


**Notes transport and interrupted batches**

The helper uses a fresh OSA language instance with a fixed send handler. Every Apple event carries `kAEDoNotPromptForUserConsent`; macOS enforces current access on each event. Ordinary reads and writes no longer depend on the blocking Automation preflight API. Status sends a fixed application-version property event and requires an actual reply; it reads no note or account content. Only an explicitly approved OS-access request uses the prompting API. Content requests normally open the fixed Notes app in the background before launching the helper. Status does not launch Notes.

Events and helper execution have finite deadlines. One completed `-1712` read-only event timeout may repeat once after source, service, mode and helper-fingerprint revalidation. The result reports `read_retry_count`. Permission denials, missing responses, consent requests and all mutations never repeat automatically. Exact-folder reads validate the target’s physical ancestry instead of walking the entire account. A timeout remains a real failure when those bounded steps cannot complete; it is never reported as empty content or successful permission.

A batch that stops during a read or authority check before its next native dispatch reports `stopped_before_dispatch`, with exact durable attempt records for any earlier verified items. Its plan stays consumed. For older failure records with a proven pre-dispatch phase, `finalize_stopped_plan` verifies the stored phase, plan hash and full completed-attempt prefix, then records a separate local finalization. The original failure stays unchanged. Mutation/verification failures, missing attempts, later dispatch evidence and unknown native effects cannot use this path. Resolving the read failure requires a new scoped batch; no write is replayed or rolled back automatically.


**Rename a Reminders list**

Prepare `rename_list` with an exact `source_id`, `list_id` and `fields: {"title": "New title"}`. The same ordinary, one-time or explicitly scoped standing-grant approval paths apply. The plan binds the writable list, sibling names and a complete bounded fingerprint of reminder IDs. Execution rechecks these before saving, then verifies the same list ID, source, writability and membership after the title change. Duplicate names, observed concurrent changes and read-only lists are refused. This changes no task content or completion state. The title can sync to existing devices or participants; EventKit does not expose participant state. Synthetic tests and a live round trip on a dedicated test list pass: its original name is restored, list identity and exact task membership are unchanged, and application access remains read-only.


The Notes helper’s watchdog shares a locked dispatch gate with the fixed JXA mutation code. Every constructor, insertion, body setter and move enters that gate immediately before the native primitive. A deadline closes the gate so later primitives cannot begin. A deadline before any entry returns a request-bound no-dispatch refusal; a deadline after entry remains uncertain. This distinction does not retroactively resolve older helper failures that lacked the gate.


**Observe one uncertain known-object move**

`notes_prepare_move_recovery` proposes accepting the current state of one exact pre-existing note ID after an uncertain single-note move. It requires the unchanged observable content and attachment identities in exactly one of the original source/destination folders, unshared physical ancestry, and a terminal helper response bound to the original request. Missing responses, ambiguous exchanges, missing/duplicated objects, changed content, other owners/sources and other operation kinds are refused.

`notes_accept_move_recovery` consumes that review under the configured strict-receipt or trusted-client policy. It records the observed source/destination location and explicitly leaves causal dispatch timing unproven. It does not move, recreate, edit or retry anything, and it preserves the original failed result. The old plan stays consumed. A successful association is a reviewed admission decision based on current verified state, not a claim that the original native operation succeeded or never ran. Later actions still use fresh snapshots and permissions.

`notes_finalize_move_recovery` completes a successful observation’s interrupted local proof. `notes_abandon_move_recovery` withdraws an unfinalized observation without clearing the original uncertainty or touching native data. A stale unconsumed observation can be replaced with a fresh review. New ordinary Notes dispatches also bind the helper request ID, request fingerprint and backend fingerprint to their immutable admitted plan before launch; identical payloads from separate attempts remain distinguishable. Older records require one unambiguous exact-request match and cannot borrow a missing response or a different attempt’s evidence.


Creation-recovery reviews also work while application access remains read-only. Accepting a matching observation changes no native data. A reviewed title-only repair grants temporary authority only for that exact candidate, original content and source; it does not enable persistent writes. The normal strict-receipt or trusted-client policy applies, and changes to source selection, helper, access modes, candidate content or approval policy invalidate the review. Existing recovery plans retain the access contract under which they were prepared.


**Targeted text edits**

Use `prepend_note` with `body` and optional `format` to insert content immediately after a separately identifiable title paragraph. Use `replace_text` with exactly `find`, `replacement` and integer `expected_matches` (1–100). Matches are literal, case-sensitive body text within individual exported text nodes. The exact original request and resulting HTML are included in the review. The title and every other exported HTML byte are retained; replacement text is escaped, with newlines rendered as line breaks. An empty replacement removes only the matching characters. If it empties a plain paragraph, readback accepts the `<br>` placeholder Notes uses for that empty paragraph. Empty formatting tags are not silently removed.

Both operations require the supported basic-format edit route. They refuse native objects, attachments, unsupported formatting, ambiguous title boundaries, wrong match counts, matches spanning formatting nodes and matches requiring entity reconstruction. They never infer a regex, fuzzy match or rich-object conversion. Readback requires the same native ID and creation metadata, complete projected content, links, and exact resulting exported HTML apart from line endings Notes inserts between complete block elements. Inline whitespace, tags, attributes, entities and preformatted content remain exact. Ordinary, one-time and explicitly scoped scenario-grant paths use the same implementation and snapshot checks. These bounds describe the current route; richer native editing remains part of the unfinished service scope.


`notes_reconcile_known_changes` independently rechecks complete returned-ID append, prepend, literal replacement, full-body replacement or move batches after a verification failure. It requires the original source scope and helper fingerprint, consumed plan, exact durable attempt records, matching returned identities and successful current adapter verification of every intended result. It records a separate readback proof, preserves the failed result and cannot replay a write. Missing returned identities, incomplete batches, mutation-phase uncertainty or changed content remain unresolved. Unlike reviewed observational recovery, this path verifies the original intended effects. It works from read-only application access and does not reactivate a revoked scenario grant.


**Reminder reference links**

`create_reminder` and `update_reminder` accept the passive `url` field. Supply an exact bounded ASCII HTTP(S), `applenotes` or `x-apple-reminderkit` URL; percent-encode non-ASCII text. Credentials, active/file schemes, whitespace, malformed escapes and values requiring silent URL repair are refused. JSON `null` clears the field. Saving this metadata never opens the URL, fetches a preview or proves that a native deep-link target exists. Rich link-preview attachments remain separate work.

One-time and scenario permissions select `url` explicitly. Readback verifies the exact stored value and retains unrequested fields. A live synthetic round trip passed web/native link storage and restoration of the original value while application settings stayed read-only. Location text writes remain unavailable through this EventKit route: the live test returned a saved reminder ID but discarded `location`, and verification rejected the partial result. Location alarms and native place semantics require their own proven implementation.


**Correct a known Reminder update**

After a single update returns its exact reminder ID but fails verification, `reminders_prepare_update_correction` can review a new corrective plan. `target: "requested"` selects the original intended public fields. `target: "before"` explicitly selects restoration of the original public fields; it is a newly authorized compensating write, not an automatic rollback. The review binds the exact object, original failure, current snapshot, chosen target and current backend. It refuses unrequested external content changes that restoration would overwrite. Only one corrective reservation is permitted for an original attempt.

Execute the new plan through `reminders_execute_approved`, then independently verify it with `reminders_reconcile_correction`. Both paths work from read-only application access using exact temporary authority and the normal strict-receipt or trusted-client policy. Settings remain unchanged. The original failure is preserved and the original plan cannot run again. A verified restoration reports `restored_before_after_explicit_correction` with `original_request_succeeded: false`; verification of the intended request retains its separate status. Missing returned identities, incomplete batches and unknown mutation effects cannot use this workflow.


**Ordinary time alarms**

`create_reminder` and `update_reminder` accept an explicit complete `alarms` array of up to 10 ordinary time alarms. Each entry contains exactly `absolute_date` (integer Unix seconds within 2000–2099) or `relative_offset_seconds` (integer seconds within one year of a timed due date with an explicit timezone). An empty array clears this ordinary set. Duplicate alarms, inferred timezones and mixed trigger schemas are refused. Alarm ordering does not define notification priority.

The review lists resolved UTC trigger times, scheduling/cancellation effects and whether past triggers may notify immediately. Apple controls notification delivery and device sync. A scenario grant must explicitly authorize the `alarms` field; ordinary note or date authority does not grant complete alarm replacement. Existing location, email, procedure, custom-sound or incomplete alarm sets require a separate fidelity-capable route. Recurring-item edits remain gated on explicit occurrence/series handling.

Readback requires the exact alarm count and values and preservation of unrequested fields. Provider truncation is a failure. Only the fixed zero-offset aliases UTC, GMT, Etc/UTC and Etc/GMT are interchangeable in date verification; region timezones and wall times remain exact. A live synthetic round trip passed absolute, relative and two-alarm scheduling and restored the original schedule from read-only settings. This proves stored scheduling metadata, not notification delivery.

`reminders_reconcile_known_changes` provides the same read-only returned-ID finalization used for Notes: it verifies complete update, completion, move or list-rename batches after a verification failure. It requires original scope/backend, exact admitted plan and attempt records, matching IDs and complete current adapter verification. It preserves the failed record and never replays an operation. Unknown mutation phases and incomplete or changed effects remain unresolved. Explicit correction/rollback previews also preserve or restore the reviewed ordinary alarm set.


**Native repeat rules**

`create_reminder` accepts `fields.recurrence` with an explicit due date. Use `set_recurrence` on an existing exact `source_id` and `id` with `fields.recurrence_scope: "exact_native_rule"` and `fields.recurrence` to change or remove that object's repeat configuration. The reminder must be uncompleted, writable and fully represented by the public metadata route. This operation preserves ordinary fields and alarms. It does not edit historical or separately generated reminders, expand occurrences, complete a recurring reminder or offer occurrence-scoped changes. Ordinary update, move and completion operations continue to refuse repeating reminders.

A rule requires `frequency` (`daily`, `weekly`, `monthly`, `yearly`), integer `interval` (1–999) and explicit `end`: JSON `null` means no end, `{"count": 3}` limits occurrences, and `{"date": 1830000000}` uses integer Unix seconds. Absolute end dates require a timed due date with a timezone and must not precede it. Count ends are bounded to 10,000; absolute ends use 2000–2099. JSON `null` for the whole rule removes repetition.

Optional filters are `days_of_week` (objects with `weekday` 1–7, Sunday first, and `week_number`, where 0 means each matching weekday), `days_of_month`, `months_of_year`, `weeks_of_year`, `days_of_year` and `set_positions`. The route refuses invalid, duplicate or frequency-incompatible filters. Empty filters retain the native due-based pattern. The calendar is Gregorian with a Monday/default week boundary; custom week starts need another route. Both construction and saved readback must retain every supported filter and end condition. Combinations ignored by EventKit fail before saving rather than silently becoming a different rule.

One-time and ordinary approval apply to the exact rule preview. Scenario grants for `set_recurrence` explicitly include both `recurrence` and `recurrence_scope`; creation grants select `recurrence` separately from title, dates and alarms. Revocation, source selection, snapshot checks and replay protection remain in force. Known returned-ID verification failures can use deterministic readback finalization or a separately reviewed exact rule correction/restoration; the original failure stays unchanged. Native framework contracts and strict/trusted stdio scenarios pass. Live synthetic tests pass daily, multi-week weekday, monthly ordinal-weekday and yearly end-date changes, followed by restoration of the original schedule. This verifies stored rule configuration, not recurrence expansion or notification delivery.


**Optional read-only Notes folder metadata**

Owners can explicitly select `native_services.notes.metadata_backend: "notes-store-readonly"`; the default is `"scripting"`. `notes_folder_role` then reads one exact selected folder's storage kind, title, parent reference and revision from the local Notes store. It binds the saved Core Data store UUID, account, entity and folder ID before returning metadata. It reads no note bodies, blobs, passwords, keys or attachment files. Regular storage kind does not by itself identify the default folder; that still requires an independent Notes scripting check. Smart, special, deleted and unknown storage kinds are not ordinary write destinations.

This is an explicit optional private-schema reader, currently live-tested on macOS 27.0 with schema checks and a macOS 27 gate. It uses Python's standard SQLite library, fixed read-only queries, a read transaction that includes the live WAL, query limits and an authorizer denying database writes, SQL ATTACH and note-content tables. It never writes the Notes database and offers no arbitrary SQL or path parameter. No database copy is created. Unknown schemas, store mismatches, unavailable accounts, denied access and timeouts are errors; they never become empty folders or automatic fallback to another host. The route is off unless the owner selects it.

On macOS 27, access to another developer team's app container or group container is denied by default, with no automatic permission prompt. The owner manages applicable access in **System Settings > Privacy & Security > Files & Folders** for the requesting host. Prefer a scoped Notes-data control when the OS exposes it. The server's selected-source queries remain narrower than the OS data permission. If the scoped control is unavailable, keep the optional route disabled while reviewing the OS access issue; Full Disk Access is a separate, broader owner choice that can expose other apps' data. It is not an automatic setup step.

The agent explains the scope, configures the selected optional route after authorization and guides the user through macOS settings; the user handles OS permission controls.
