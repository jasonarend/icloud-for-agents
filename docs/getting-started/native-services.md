# Native Notes and Reminders development setup

Current implementation is a development increment with bounded reads and guarded creation plans; full service support is still incomplete. Native Notes and Reminders are independently disabled by default. Existing Mail/Calendar/Contacts configuration and approval modes are preserved.

**Current capabilities**

Reminders exposes OS permission status, source discovery, selected-source list discovery, bounded task pages, date/timezone-filtered daily and inclusive date-range queries with priority filters and exact task reads through public EventKit, including structured public recurrence and alarm metadata. Native tags, hierarchy and attachments remain outside those public metadata projections. Notes exposes account discovery, selected-account folder discovery, bounded note-title pages, title/plaintext and exported table-text search, attachment metadata and unlocked note text/HTML reads through built-in JXA automation. Advanced native metadata is explicitly incomplete. Offset pages may shift during external edits. Access-status tools report effective service scope and approval policy without contacting Apple. Opted-in services register exact creation proposals, approved execution, scoped status and read-only known-ID reconciliation. Notes currently supports creating notes and root folders, appending to supported existing notes and explicitly replacing a supported note's complete title/body; Reminders supports creating lists and tasks with notes, priorities and explicit dates, updating selected task fields, setting completion and moving tasks between writable lists in the same source. Both global and service access must be write-enabled. Strict local receipts remain the default; owner-selected trusted-client mode retains its existing authorization contract. Standing grants, general native-object edits and Notes organization operations remain incomplete. Existing-note body rewrites require a saved, unlocked, unshared note with no attachments or unsupported exported structures. Appends must retain the original exported HTML as an exact prefix during readback; whole-body replacement requires an explicit complete title and body. Recurring reminder edits require occurrence/series handling and are refused.

**Owner-controlled setup**

An authorized agent can build the repository-owned helper with `scripts/build-native-helper.py`, using a new output directory for each reviewed build. Swift and codesign are macOS build-time tools; neither a separate MCP server nor an additional Python runtime dependency is required. The resulting app is ad-hoc signed for development. A release still needs its own signing/distribution and upgrade-permission continuity evidence.

After the owner selects a service, private settings accept `native_services` alongside the optional `notes` and `reminders` service booleans. For example, these nonsecret fields illustrate the schema; they do not enable a live installation:

```json
{
  "native_services": {
    "notes": {"access_mode": "read-only", "source_ids": []},
    "reminders": {
      "access_mode": "read-only",
      "source_ids": [],
      "helper_path": "/absolute/path/to/iCloudAgentsHelper.app/Contents/MacOS/icloud-agents-native"
    }
  }
}
```

Empty source allowlists permit source metadata discovery only. Select exact returned IDs under owner authorization before listing containers or reading content. Do not infer native source identity from the configured IMAP login or account display name. The launcher never forwards inherited native opt-ins or native configuration.

The helper accepts protocol-versioned JSON on stdin. It includes fixed Notes and Reminders creation transports for the approved-plan executor; there is no arbitrary script or command action. Internal transport availability is not authorization to mutate data. Normal MCP reads cannot request a grant. An explicit local `request_access` helper action asks macOS for Reminders full access; the human handles the system dialog. That OS grant never enables application writes. Notes can optionally use the same helper path, which embeds the fixed JXA bridge and declares its Automation purpose. Helper status checks do not prompt; the explicit Notes permission action uses the normal macOS consent flow. The built-in osascript read route remains available when no Notes helper is configured. The helper launches as a normal macOS application for its own consent context, using an owner-private one-shot request/result directory under local Application Support, separately namespaced for each approval ledger. Moving the transport does not move or clear the ledger; retained requests from the previous transport remain visible. Error responses are retained for diagnosis and are never replayed automatically. Neither route resets or bypasses denied permissions. Permission-check timeouts are reported as unverified access, not as an empty account or a successful grant. Permission attribution depends on the launch host and must be validated per client. Do not reset privacy databases or bypass a denied prompt.

Opted-in services also expose `notes_prepare_os_access` / `notes_request_os_access` and their `reminders_` equivalents. The first tool creates a reviewed consent-request proposal; the second consumes it once under the existing strict-receipt or owner-selected trusted-client policy. The proposal describes the OS-level access, which is broader than the server's selected-source and read/write controls. The user handles the actual macOS dialog. A completed request reports granted, denied or unverified status separately and never selects sources or enables application writes. Timeouts do not trigger another prompt. Source selection and application-access elevation remain separate owner-controlled setup steps in this increment.

The agent handles supported setup steps; terminal commands remain an optional owner/operator path, consistent with existing services. Existing strict receipt and trusted-client workflows are not replaced by native OS permission grants.

**Validation status**

Offline tests cover independent service selection, stale-tool refusal, missing scope, disabled access, input bounds, fixed JSON dispatch, environment filtering and response failures. A compiled helper status check is native execution evidence only; full access, content reads and cross-device sync require their own live acceptance. Live development acceptance has exercised selected-source reads, dedicated test containers, rich and plain Notes, and representative Reminders. Live Notes creation has exposed title/body assignment and temporary-to-permanent identity transitions. Content readback confirms the body-only constructor saved its fixture, and synthetic regression tests cover unrelated draft transitions and ambiguous candidates; fresh real stdio creation now passes prepare, execution, independent readback, status and replay refusal for both services. A real stdio read-only fixture workflow also verifies table-text search and reminder range/priority queries with public metadata; creation proposals remain refused in read-only mode. Real stdio append/replacement tests also pass, including refusal to rewrite an existing native table. A basic-format fixture retains its original HTML prefix, bold, italic and link through append. These readback checks are not a claim of full native-object or visual fidelity. Live development tests also cover reminder field edits, completion/reopening, due-date clearing and same-source moves. EventKit can synthesize a start date during a due-date change; updates explicitly preserve the reviewed start value. A single known-ID reminder update with failed readback can receive a separately approved correction proposal. Both original and corrective audits remain immutable, and independent readback must verify the original requested state before admission resumes. This route cannot retry creations, unknown mutations, incomplete batches or recurring tasks. Uncertain single-note creations with no returned ID have a separate explicit recovery proposal. An authorized client can accept one fully matching observed note or repair an exact title-only candidate using the original request. Source, folder, title uniqueness, lock/share state, attachments, before snapshot and complete requested content are checked. Recovery follows the selected strict/trusted policy; trusted-client review is not independent proof of human review. It records an association rather than claiming the provider returned that creation ID. Original failure records remain unchanged. A read-only finalize tool can complete an interrupted successful recovery proof. This is not a generic uncertainty clear or a creation retry. Failed or uncertain plans are retained and never replayed automatically. Rich fixtures and write testing require read-only success in both services and the separate write-access approval gate. These checks do not establish full feature, client-host, notification-delivery or cross-device acceptance.
