# Approval policies

Default: `local-receipt`. Missing configuration preserves the existing owner receipt checks. An optional owner-controlled `approval_policy: "trusted-client"` in private `local/settings.json` opts into reliance on the connected client's authorization workflow. This is an ongoing authorization change requiring explicit owner approval before activation. It does not create credentials, grant new provider permissions or disable ChatGPT confirmations.

The trusted-client policy authorizes execution of exact send, recoverable Trash and ordinary calendar/contact proposals without an independent local receipt. The assistant must follow actual owner instructions, obtain recipient/content approval for sends, and request clarification or confirmation where scope or impact requires it. The server does not receive cryptographic evidence of chat consent and cannot independently determine that a tool call was human-approved. Audit records say trusted-client policy, not verified human receipt. There is no approved boolean input and no fabricated receipt. Trust every client with access to this private instance accordingly; do not offer this as isolated per-user authorization on a shared deployment.

Account binding, proposal expiry, exclusive durable started markers, account-wide unfinished/uncertain-write blocking and immutable hash audit remain enforced. DAV ETags, resource identity checks, exact mail folders, UIDVALIDITY, bounded batches and safe move semantics are unchanged. Failed, partial, unknown or missing results require reconciliation before another trusted proposal write. Same-plan replay remains refused. Irreversible DAV delete proposals still require independent local receipts; permanent mail purge remains absent and invitation replies unsupported. A separate gate is intentionally retained for irreversible data loss.

Cleanup scope is a separate policy: source folders, destinations, operations, per-batch size and revocation remain explicit. Optional `max_24h: null` means no aggregate daily cap; optional `days: null` in a reviewed grant request means no automatic expiry. Neither changes the safe batch bound (1..100), provider constraints, audit, exact identity checks or uncertain-outcome blocking. Multiple daily runs are supported. Owners may choose positive aggregate caps and expiration instead. No 100/day or 30-day requirement is imposed.

The launcher reads the policy only from validated private settings, never an inherited policy environment variable. Unknown modes fail closed. Activating either policy requires review of its exact scope, updating owner configuration and an idle service reload. This document and code do not activate it. Expired plans must not be extended or replayed.

OpenAI documents context-dependent client write confirmations in [custom MCP connections](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt). Standard [MCP elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation) requires client capability support. Actual elicitation support through this ChatGPT tunnel has not been established; this policy does not claim it has.


## Narrow no-effect recovery

One failed calendar-create attempt may be recovered only through a separately reviewed local reconciliation transition, never an exposed approval/recovery tool or automatic retry. It preserves original plan, started marker and failure result. Evidence binds exact URL/UID, original request hash, a supported bounded UID absence check, GET404, timestamp and identified material fix. One identical-payload retry is reserved durably and proof freshness is checked before admission. The executor repeats exact GET404 before a conditional If-None-Match:* PUT. A second immutable record requires successful same-resource readback before future trusted writes are unblocked. This is a trusted local operator workflow; local files are not cryptographic proof of a human or provider response. No generic retry, uncertainty clear, expired-proof extension or irreversible-action bypass exists.


## Different clients, same server checks

All clients call the same server-enforced account, folder, identity, snapshot/ETag, expiry, replay and uncertainty checks. Markdown instructions cannot disable those checks. A client UI can add its own confirmations, but tool annotations and a model saying "approved" are not independent authentication. Strict local receipts use the local human workflow; trusted-client mode intentionally relies on that connected client honoring owner authorization. Its assertions are audited honestly. Standing grants apply to the configured single-account instance, not cryptographically identified client sessions; attaching another client shares that instance's scope. Do not expose it as multi-user isolation.
