# Notes and Reminders operations for assistants

This technical reference covers setup, permissions, tool inputs, operation limits and recovery for assistants. For a short setup guide, see [Set up Notes and Reminders](../getting-started/native-services.md); for capabilities, see the [overview](native-support.md).

Start with [helper and permissions](#notes-permission-identity) and [service configuration](#owner-controlled-setup), then verify reads before [one approved action](#one-approved-action-from-read-only-access) or [ongoing permissions](#ongoing-and-scenario-permissions). For recoverable removal, use the separate [Notes](#recoverable-notes-removal) and [Reminder family](#recoverable-reminder-families) instructions. The remaining sections describe individual tools and their exact limits.

Choose Notes, Reminders, both, or neither. Each service starts disabled and has its own selected accounts and read/write controls. Your agent can help set up the helper, verify read-only access, and prepare exact changes or ongoing permissions for your review. The capability overview describes the supported operations and their limits. The shared helper routes the requested service before querying permission state; a Notes request does not query Reminders permissions, and unknown services are refused. Existing Mail/Calendar/Contacts configuration and approval modes are preserved.

## Current capabilities

The `notes_access_status` and `reminders_access_status` tools report available operations and configuration requirements through `implemented_write_operations`, `unavailable_write_operations` and `unavailable_feature_families`. Unavailable operations are listed with reasons. `provider_capabilities: "not_probed"` and `operation_listing_is_authorization: false` distinguish this local implementation inventory from OS consent, a verified provider capability or permission to execute a change. Read-only status does not contact either app.

Reminders exposes OS permission status, source/list discovery, bounded task pages, daily and inclusive date-range queries, priority filters and exact reads through public EventKit. Structured public recurrence and alarm metadata is available; native tags, hierarchy, attachments and other advanced metadata remain incomplete. Approved changes cover list/task creation, list renaming and explicit sRGB list colors with membership readback, selected task fields and completion/reopening. The optional native backend adds the separately described tags, hierarchy, list/group organization, Smart Lists, templates, attachments and recoverable deletion routes. With the explicitly selected ReminderKit backend, bounded same-source root moves keep every reviewed descendant together; the default EventKit backend refuses moves. Ordinary edits of recurring tasks are refused. Explicit native repeat-rule creation and changes use the separately scoped recurrence operation described below.

`reminders_query` also accepts `created_from`, `created_before`, `modified_from` and `modified_before` as UTC timestamps, with inclusive lower and exclusive upper bounds. Each filter excludes reminders whose corresponding timestamp is unavailable and reports that exclusion. Follow live-offset pages; concurrent changes can shift them. This is a bounded view of existing items, not a change log, deletion detector or proof of complete synchronization.

`reminders_export_page` returns a versioned JSON observation of one requested list within selected sources, up to 20 reminders and one million encoded bytes per page. Follow `next_offset` until `done`; list changes can shift pages, and an empty page does not establish that the requested list exists. It includes public fields and per-item coverage, and explicitly omits native tags, hierarchy, attachments and advanced metadata. It does not write a file or change Reminders. This is not an atomic backup or a restorable export; identifiers and public recurrence or alarm observations may be incomplete.

`reminders_prepare_observation_copy` turns up to ten items from a supplied observation page into a reviewed proposal to create copies in one exact selected list. The caller must explicitly accept the omissions; copying due/start dates and URLs is individually optional. Every new reminder starts incomplete. Original identifiers, completion state, native tags, hierarchy, attachments, recurrence, alarms, location, sharing and timestamps are not copied. The supplied observation may be stale or incomplete, and copies may duplicate existing reminders. Date copying refuses unsupported or subminute times. Use ordinary one-time approval, or supply an active grant explicitly scoped to `copy_observation`; a generic `create_reminder` grant cannot be passed to this tool. A generic creation grant still allows its approved fields to be filled from caller-provided content through the ordinary creation tools. Scenario-grant limits, expiry and revocation apply. Source checks, unfinished-write guard, verification and no-replay behavior still apply. The proposal binds its limitations and options into the approval digest; it is not a restore. Native metadata and cross-device fidelity remain unverified.

`reminders_export_ical` returns a single read-only [iCalendar VTODO](https://www.rfc-editor.org/rfc/rfc5545.html) with title, notes, completion, priority, supported URLs and location text, and supported date-only or zoned start/due values. Available creation, modification and completion timestamps are included to whole-second precision; unavailable timestamps and fractional seconds are omitted. Unambiguous zoned times are converted to UTC, without retaining the original timezone label. Supported absolute display alarms are included with text generated from the reminder title; importing can schedule notifications. It refuses ambiguous or nonexistent local times, unsupported URLs, relative or location alarms, recurrence, incomplete public metadata and mixed date types rather than guessing. The result reports omitted fields, including native tags, attachments, hierarchy and collaboration metadata. Its generated UID is pseudonymous; the output is not a complete or restorable backup.

`reminders_prepare_ical_copy` accepts a bounded, CRLF-delimited iCalendar object containing one VTODO with explicit UID, timestamp, summary, status and supported priority. It accepts date-only or whole-minute UTC start/due values and up to ten absolute display alarms in 2000–2099; it refuses recurrence, relative or other alarm types, other components, unknown properties and unsupported parameters. It prepares a lossy copy: the caller explicitly accepts omissions and can select whether to copy dates, URLs and supported alarms. Copied alarms may schedule notifications and their display text may change; completed tasks become incomplete copies and location and timestamps are omitted. The original iCalendar digest and those effects are bound to the proposal. Use one-time approval or an explicitly scoped `copy_observation` grant that includes any selected alarm field. Live copying of alarms and grant-backed iCalendar copies remain unverified.

`reminders_default_list` reads the system default through EventKit. It returns list details only when the list belongs to a selected source; an unselected default is reported without revealing its identity. No default or an older helper without this operation is reported separately. It does not change the system default or enable writes.

With the optional ReminderKit backend, `reminders_list_features` reads the provider’s grocery-categorization, shopping-session, group and sharing flags for one exact selected list. These observations do not identify every native list type or expose participants or their permissions, and do not change the list. Read category IDs and titles separately with `reminders_list_sections`. Live shared-list behavior remains unverified. These flags require the updated native helper. With `include_pinned: true`, the same exact-list read also reports the native pin flag; the default response does not request it. This does not change pin state or establish list ordering. The opt-in pin observation requires the newer helper. Section, subtree-move, recovery, pin and badge plans bind these observed flags; other write plans do not yet bind them, and sharing may change after a read. Unsupported native interfaces refuse the read.

With the optional ReminderKit backend, `reminders_list_sections` reads up to 100 ordinary native section IDs and titles for one exact selected list. The helper verifies each section's account and list identity and sorts results by ID; this is not the app's display order. `reminders_get` can separately request `include_native_section` for one reminder. A reported section is verified against the selected account and list; `provider_not_reported` means the relationship is unknown, not that the reminder has no section. Unsupported native interfaces or inconsistent identities refuse the read. `create_section` accepts an exact source, list and title through the ordinary approval, one-time and scoped-grant paths. Section writes refuse when the provider reports grocery categorization, a grocery shopping session or a list group, and bind the observed flags before dispatch. Those flags do not prove the complete list type, so behavior on special lists remains unverified. It preassigns an ID and checks the observed section inventory and list reminder membership before and after saving; order and complete section membership remain unverified. `rename_section` targets one exact section ID and preserves the observed list inventory and reminder membership; scenario grants must explicitly name each section ID. Moving or deleting sections is not yet supported.

With the explicitly selected ReminderKit backend, `reminders_list_parent` observes the provider-reported parent group of one selected list. A returned group must match the same source and the list’s native parent identity; an unreported parent is not proof of a complete hierarchy. `reminders_group_lists` can separately observe bounded pages of provider-reported child lists in one exact selected-source group, checking each child account and parent identity and reporting the provider’s group flag for each child. It accepts up to 1,000 reported children and pages may shift when the group changes; follow `next_offset`. `reminders_inspect_group_hierarchy` follows these provider-reported group edges with explicit node and depth limits, rejecting repeated or cyclic IDs. Its separate reads can drift and it reports unexpanded groups. None of these observations proves complete hierarchy, membership or order, and none enables moving lists. An updated helper is required.

With the explicitly selected ReminderKit backend, `reminders_smart_lists` lists bounded custom Smart List IDs and titles in one selected source. The helper checks account and record identities, refuses unknown or oversized provider collections, and sorts pages by ID; the pages may shift as lists change. This does not include built-in views, filter rules or matching reminders, and does not create or modify lists. An updated helper is required.

With the explicitly selected ReminderKit backend, `reminders_templates` lists bounded native template IDs and titles for one selected source. It verifies each template belongs to that account and refuses unknown provider shapes, duplicate identities or inventories over 1,000 records. Pages are sorted by ID and can shift if templates change. `reminders_template_sections` can inspect bounded provider-reported section IDs and titles on one exact template; account and parent identities are verified, while complete section coverage, display order and reminder membership are not. The listing does not expose template reminder contents or sharing links and does not create, edit, instantiate or delete templates. A populated template section has not been verified live. An updated helper is required.

With the explicitly selected ReminderKit backend, `reminders_get` accepts `include_native_assignment: true` for one exact reminder. It reports whether the provider returned a current assignment and the count of assignment records, without exposing identities or inferring the assignee, permissions, notifications or completeness. Unsupported or inconsistent provider data is refused. `reminders_query` and `reminders_daily` can filter on `has_current_assignment` using that same provider observation, with bounded pages and the usual continuation behavior. This is not an “assigned to me” filter. A live assigned reminder and assignment changes have not been verified. An updated helper is required.

With the explicitly selected ReminderKit backend, `reminders_get` accepts `include_native_attachments: true` to inspect up to 100 native attachment records for one exact reminder. It returns scoped record IDs, observed native kinds and optional type identifiers; it does not return file paths, URLs or content. Unknown record types, inconsistent identities and oversized collections are refused. The observation does not establish that all attachment representations are covered. `reminders_query` and `reminders_daily` can filter `has_native_attachments` by whether the provider returned any of these records; an empty observation is not proof that every possible representation is absent. Follow bounded pages to completion. Exporting, adding or removing reminder attachments is not supported by this read. An updated helper is required.

An optional `reminders_get` request with `include_native_early` reads the selected reminder's separate native early-reminder offsets. It reports observed native values and a separate interpreted offset, without delivery guarantees. Units 0, 1 and 2 represent minutes, hours and days; the native interval model identifies units 3 and 4 as weeks and months. Negative counts indicate before the due date. Other units are not interpreted; these are distinct from EventKit time alarms. The helper checks the account and reminder identity and refuses unavailable or malformed provider data. An empty observed payload means no early offset was reported by the provider at that read. `add_early` creates one offset in minutes, hours, days, weeks, or months on an incomplete or completed timed reminder only when the provider reports an empty early-alert state; its one-time proposal and scoped scenario grants explicitly review notification effects. Independent readback checks the offset and observed native metadata. Week and month creation has not been verified against the live provider. Changing its timed due date reviews the resulting early-notification reschedule. Removing the timed due date is refused while an early reminder is observed; use a separately approved `clear_early` operation first. It takes exactly `fields: {"clear": true}` and removes one observed existing early offset, binding the complete provider payload fingerprint and native alert UUID. Due date, ordinary alarms, content and other observed native metadata must remain unchanged. One-time approval and exact-list scenario grants selecting `clear_early` and field `clear` use the same checks. A closed dispatch gate, changed fingerprint, multiple alerts or unsupported native metadata refuses the save. Updating an offset uses a reviewed clear followed by a fresh reviewed add; those are separate operations, so a later failure is reported as partial success without automatic replay or rollback.


Notes exposes account/folder discovery, bounded title pages, title/plaintext and exported table-text search, attachment metadata and unlocked text/HTML reads, with an optional bounded Markdown view and explicit conversion-loss metadata. Approved changes cover note and folder creation, supported-note appends and prepends, exact literal text replacements, and explicit complete title/body replacement. The default scripting-only configuration limits content writes and nested-folder creation to the account's default creation folder. With the explicitly selected read-only metadata backend, the normal Notes writer also supports verified ordinary folders and their private ancestors. The optional native-model route remains a separate backend. Notes moves require the explicitly selected `notes-store-readonly` metadata backend, existing host permission to read the fixed folder metadata and an updated helper. Source, destination and their ancestors must have verified ordinary, nondeleted, nonsmart roles and remain unshared in the same selected account. The executor refreshes the snapshot before dispatch; the helper checks the bound folder identities, titles, parent relationships, sharing, note content and attachment inventory before moving the existing object. Readback checks native identity, observable content, attachments, roles, source absence and the independently read saved physical folder. Scripting-only location changes cannot report success. These separate reads are not an atomic provider transaction. The default scripting-only configuration refuses moves. Ordinary moves exclude special folders. Recoverable removal and restoration have their own system-folder checks, described below. Body rewrites refuse existing attachments, tables/checklists and unsupported exported structures. Appends must retain the original exported HTML as an exact prefix. New move proposals therefore require the explicit metadata role checks; old proposals without them remain inadmissible. Folder creation accepts an optional exact `parent_folder_id`; omitted means the selected account root. Nested creation binds the private parent and its ancestors, checks direct siblings for duplicate names, and verifies the returned folder’s physical parent. These local observations do not establish every client’s permission behavior or cross-device fidelity.

`notes_export_observation` returns a versioned JSON observation of one exact scoped note using the ordinary Notes read. It includes bounded HTML and plaintext for an unlocked note and reports truncation; for a locked note it returns only its scoped identity and unavailable-content status. Concurrent edits can affect the read. It does not unlock notes, fetch attachment content or write a file. Native objects, attachments and collaboration details are omitted, so this is not a complete backup or restorable export.

`notes_format_list_markdown` converts a bounded subset of plain headings, single-line paragraphs and nested unordered or consecutive numbered lists into HTML. It reads no Notes data and makes no change; pass its HTML to a separately reviewed Notes creation or edit with `format: "html"`. It refuses inline Markdown, links, tables, code blocks, checklists, unsupported indentation and nonconsecutive numbering rather than guessing. Its lists are HTML formatting, not native Notes checklist items, and formatting round trips are not guaranteed. Notes normalizes item containment in its HTML export; the Markdown view preserves nesting for that shape. Native checklist semantics, visual styles and cross-device behavior remain unverified.

`notes_inspect_exported_links` observes link elements in the bounded HTML export of one exact selected note, in pages of at most 50. Link labels and targets are untrusted note content, including potentially unsafe schemes; the tool does not open, resolve or verify them. It omits invalid or oversized targets, reports source truncation, and can check `expected_modified` on later pages. Locked notes return unavailable content rather than an empty link list. `html_links_complete` is false for unfinished link markup or a truncated export; it does not establish native-link completeness. Notes can change during or between reads, and native links inside objects, link identity and backlinks remain unverified.

`notes_format_plain_table` converts bounded rows of single-line plain text cells into escaped HTML for a separately approved Notes creation or edit. Rows must have equal width; merged cells, native table identity and round-trip fidelity are not represented. This formatter does not read or write Notes. Visual rendering and cross-device synchronization remain unverified.

`notes_find_html_references` looks for one exact decoded link target in the bounded HTML exports of up to three notes from one selected physical-folder page. It returns only matching note identities and titles, plus locked, truncated, unfinished-link or unavailable observations. It never opens the target. On a read failure it stops without retrying or silently skipping the failed note; restart the scan after resolving the failure. Follow folder pages when available, but do not treat the result as complete native backlinks: notes can change between reads, and native objects, other folders and unavailable content may contain additional references.

`notes_prepare_observation_copy` accepts one supplied unlocked, nontruncated observation and prepares a reviewed copy into one exact selected folder. It requires explicit acceptance of omissions and a verifiable title/body boundary; unsupported HTML is refused by the ordinary Notes creation adapter. The original identity, native objects, attachments, collaboration, sharing and timestamps are not preserved, and formatting may change. The observation is user-supplied and may be stale, and a copy may duplicate an existing note. Use ordinary one-time approval, or an active grant explicitly scoped to `copy_observation`; a generic `create_note` grant cannot be passed to this tool. A generic creation grant still allows its approved fields to be filled from caller-provided content through the ordinary creation tools. Scenario-grant limits, expiry and revocation apply. Folder-role, source, unfinished-write and verification checks remain in force; this is not a restore. Full native object fidelity and cross-device behavior remain unverified.

For `notes_search`, `match_scope: "plaintext"` searches titles and bounded plaintext without separately fetching exported HTML for table text. This can reduce work on a slow search but can miss text available only in a table projection; the result states that limitation. `match_scope: "title"` avoids body reads altogether, and the default `all` retains the separate bounded table-text search. None of these modes guarantees that a stalled Notes app or a particular note will respond.

`notes_default_folder` reads the default folder of one exact selected Notes account. The result includes the folder identity, parent, title and sharing status; it does not change the default, grant access or establish roles for other folders.

Ordinary change preparation requires both global and service access to be write-enabled. Exact one-time plans and separately activated standing grants also work from read-only access, as described below. Strict local receipts remain the default; owner-selected trusted-client mode retains its existing authorization contract. Access-status tools report effective scope and policy without contacting Apple. General native-object edits and broader folder organization remain incomplete. Offset pages may shift during external edits; follow next_offset until done, including empty filtered pages.

## Notes permission identity

The bundled helper is part of iCloud for Agents. Your assistant builds and configures it during setup; you handle the macOS permission windows. You do not need to install a separate product or run terminal commands.

For Notes, approve the Automation request for the configured helper. The default app is named `iCloud for Agents.app`, although an existing installation may use an older name. macOS chooses the name shown in its permission window. Use the configured app launch route: running the executable directly can have a different permission context.

Ask your assistant to check `notes_status` before reading a selected folder. Status checks do not request permission or read note content. If access is denied, check the entry for the configured helper in **System Settings → Privacy & Security → Automation**. If Notes is unresponsive, quit and reopen it normally, then have the assistant inspect the failed request before continuing. An enabled switch alone does not confirm that the running helper can read Notes.

Normal Notes setup does not require Full Disk Access, Accessibility or the optional Notes-store backend. Advanced features that need additional access are described in their own sections below. The `requester_identity` diagnostic in `notes_status` can help identify the running helper; it does not establish which name macOS displayed in a consent window.

## Owner-controlled setup

Start with a simple request to your assistant, such as: “Connect Notes and Reminders, let me choose the accounts, and keep both read-only.” You can choose either service independently and change that selection later.

1. **Prepare the helper.** The assistant builds the repository-owned helper with `scripts/build-native-helper.py` in a new output directory, preserving an existing working installation. The build selects a matching macOS SDK for the available developer tools. Swift and codesign are build-time macOS tools; no additional Python runtime dependency is required.
2. **Enable your chosen services.** The assistant uses `scripts/configure-native.py` to review the helper path and service settings. Newly enabled services start read-only. Existing services, Keychain references and approval policy are preserved.
3. **Restart the connection.** After enabling a service or changing its helper, the assistant restarts the affected client/server connection so it exposes the chosen tools and settings. A running server retains its previous settings.
4. **Approve macOS access.** The assistant prepares an access proposal with `notes_prepare_os_access` or `reminders_prepare_os_access`, opens the local review window, and executes the approved request with the corresponding `request_os_access` tool. This local review is required even if trusted-client approvals are enabled. You respond to the macOS dialog yourself. A refusal or timeout does not trigger another prompt automatically.
5. **Choose accounts.** An empty `source_ids` list permits account discovery only. Select the exact returned accounts before the assistant reads folders, lists or content. Notes and Reminders account IDs are independent of the Mail login and display names.
6. **Apply the account selection.** The assistant applies the reviewed source IDs and restarts the affected connection again. If the selected IDs already match the saved settings, no further settings change is needed.
7. **Check a small read.** Ask the assistant to show a small page of Notes folders or Reminders lists from the selected accounts. Confirm the result before approving any content changes.

macOS grants and iCloud for Agents permissions are separate. Reminders' OS grant can cover all available sources and include write access; the server still enforces your selected accounts, read-only mode and change approvals. Granting OS access does not enable a service, choose an account or authorize writes. Notes and Reminders each need their own permission.

For an existing installation, the assistant supplies `--service notes` or `--service reminders`, the exact helper executable with `--helper`, and repeated `--source-id` values to `scripts/configure-native.py`. The default invocation previews the change and its digest. After your authorization, `--apply-review <digest>` applies that exact review and creates a private settings backup. The utility refuses stale reviews, changed helpers and unfinished or uncertain writes. Omitted source selections preserve existing IDs; `--clear-sources` returns a service to discovery-only access. Use `--disable-service` to disable a service, then restart its server connection.

These nonsecret fields illustrate the private settings schema:

```json
{
  "native_services": {
    "notes": {"access_mode": "read-only", "source_ids": []},
    "reminders": {
      "access_mode": "read-only",
      "source_ids": [],
      "helper_path": "/absolute/path/to/iCloud for Agents.app/Contents/MacOS/icloud-agents-native"
    }
  }
}
```

The helper is ad-hoc signed by default. A builder can choose an existing local certificate with `--sign-identity` after the certificate owner's authorization; the owner handles any Keychain prompt. Source installations do not need the maintainer's signing key. Signing does not grant macOS access or guarantee that permissions survive a helper upgrade. Preserve the existing helper and verify access after replacing a build.

The server launches bundled Notes and Reminders helpers as macOS apps. Legacy standalone Reminders helpers retain their direct launch. If a helper or its launch identity changes, prepare a fresh proposal or grant when the existing approval no longer matches. Keep previous audit records, especially unresolved operations. Terminal utilities remain available for operators who prefer them; the assistant-led workflow covers setup and approvals.

### Permission and connection troubleshooting

Check `notes_status` or `reminders_status` and the actual read result before changing settings. Status distinguishes granted, denied and unverified access; a timeout is not an empty account. The helper's fixed operations cannot reset privacy permissions or bypass a denial. If a permission entry points to an older helper, have the owner review the configured app in System Settings.

A `transport_warning: "launcher_nonzero_result_received"` means macOS reported a launch error after the helper had already returned a valid result. Notes permits this only for nonprompting status checks; Reminders can also return a verified read with this warning. Permission requests and writes still require a successful launch. The assistant should inspect the warning and pending request status rather than replaying an operation.

## Verify access before making changes

Start with a bounded read from a selected account, then review one exact change or the scenario scope you want to allow. Setup approval does not authorize unrelated writes. Read results describe the local provider state; they do not guarantee notification delivery or cross-device synchronization.

A save error, timeout or missing response after a write may leave its outcome uncertain. Do not repeat the write automatically. The service's readback and separately reviewed recovery tools can inspect the result while preserving the original failure. A confirmed refusal before dispatch consumes its plan and reports `refused_without_dispatch`; use a new proposal after resolving the cause.


## One approved action from read-only access

Use `notes_prepare_once` or `reminders_prepare_once` with the same exact change dictionaries as the ordinary proposal tool. Review the returned batch and execute its plan ID with the service’s `execute_approved` tool. The configured strict local receipt or trusted-client policy still applies. This path requires an enabled service, selected sources and OS access; it cannot enable a disabled service or select another source.

Temporary authority covers only the exact consumed batch. It exists around each individual dispatch and ends on success or failure, including when a captured execution context outlives the call. Settings and environment stay unchanged, and a restart does not leave an unrestricted write window. A saved unconsumed plan can resume within its expiry only if access, backend, source scope and approval policy still match. Each item rechecks current authority and content; replay and uncertain-outcome protections remain in force. Use the service’s `cancel_plan` tool to withdraw an unstarted change plan; cancellation persists across restarts and cannot recall an in-flight operation.


## Ongoing and scenario permissions

Use the service’s `prepare_grant` tool to propose a scenario scope, then `activate_grant` after review. In strict mode, your assistant requests a local review window where you can approve the exact scope; owner-selected trusted-client mode uses the existing client authorization policy. The activation review explicitly grants future batches inside its rules without another per-batch receipt. Mail grants never authorize native services.

A scope contains `scenario`, `rules`, `max_batch`, `max_24h` and `expires`. The scenario is a human-readable reference, not a natural-language content filter. Each rule specifies one exact `operation`, `source_id`, `container_id`, allowed input `fields`, and `destinations`. Use an empty destination array for ordinary operations; moves require exact destination IDs, while `create_subtask` requires exact parent reminder IDs in `destinations`. Current rules cover the service’s implemented ordinary operations only. Unsupported operations, permanent deletion, collaboration changes, invitations, lock/password changes, recording and external export are excluded.

For example, a Notes meeting-summary scenario can allow `create_note` with `title` and `body`, or `append_note` with `body`, in one exact private folder. A Reminders action-item scenario can allow `create_reminder` with `title`, `notes`, `priority` and `due` in one selected list. A create-folder rule selects its exact parent folder or account root; create-list selects its source root. Existing reminder actions bind the item’s physical list. Field authorization refers to supplied input fields; adapter-derived content and preservation checks remain visible in each immutable batch review.

For a Notes move scenario, select `move_note`, `fields: ["destination_folder_id"]`, one exact source folder as `container_id`, and exact ordinary destination IDs in `destinations`. Select `notes-store-readonly` explicitly before preparing the grant. Preparation, activation and batch admission recheck source/destination ancestry, sharing and ordinary storage roles. Role revisions may advance as membership changes, but names, roles, parent relationships and account bindings must stay unchanged. Each moved note still has an exact content and attachment snapshot. A return move requires its own rule with the two folders reversed. Recently Deleted and cross-account destinations are refused.

For a copy scenario, select operation `copy_observation` instead of generic creation. Notes copies require `title`, `body` and `format`; Reminder copies require `title`, `notes` and `priority`, with `due`, `start`, `url` or `alarms` included only when the owner wants those optional fields copied. Only the iCalendar copy route can select supported absolute alarms. Use the exact destination folder or list as `container_id` and an empty `destinations` array. After activation, pass the grant ID to the service's `prepare_observation_copy` tool or `reminders_prepare_ical_copy`, not `prepare_with_grant`. The grant review describes the loss and duplicate risks; each immutable copy batch still records its particular omissions and options.

`max_batch` is 1–20. Set `max_24h` and `expires` to JSON `null` when the owner selects no aggregate cap or no expiry. A numeric expiry is a Unix timestamp. Admitted items count conservatively against the rolling cap, including failed or uncertain items. Quota reservations survive interruption and are not silently refunded. Grants survive server restarts while the same owner, service modes, backend fingerprint, source selection, approval policy and container metadata remain valid. Use `prepare_grant_replacement` to review before/after scope, then `activate_grant` on the returned ID. Activation retires the exact prior grant before the new scope becomes active; its rolling quota history carries forward. A denied or stale replacement leaves the prior authority unchanged. Interrupted admitted replacement is inactive until its original proof is finalized; it never silently revives either scope.

Use `prepare_with_grant` with the grant ID and exact changes, then `execute_approved` with the returned plan ID. This never changes read-only settings or opens a general write window. It rechecks the active grant, source/container, operations, fields, bounds and native snapshots before admission and each dispatch. Replay and uncertain-outcome protection still apply. `grant_status` reads the saved scope and current activation context without refreshing provider containers. Its separate `write_admission` field reports unfinished native operations that block an otherwise active grant. `revoke_grant` immediately prevents new admissions and remaining batch dispatches; it cannot recall an already in-flight effect. An unstarted batch can also be cancelled with `cancel_plan`.

If activation was admitted but its completion record was interrupted, `finalize_grant` verifies that original admission and completes only the local audit. It does not mint a receipt, issue another OS request, or write native data. Revoking an interrupted activation leaves it inactive and allows its no-data lifecycle to settle.

Optional terminal parity is available through `icloud-agents-native-access --service notes` or `--service reminders`, with `prepare --scope-file FILE`, `replace GRANT_ID --scope-file FILE`, `activate GRANT_ID`, `finalize GRANT_ID`, `status GRANT_ID`, `revoke GRANT_ID`, and `changes GRANT_ID --changes-file FILE`. Use the same owner configuration as the MCP server. The agent-led MCP path covers the same operations; terminal commands are an operator choice.


## Notes transport and interrupted batches

The helper uses a fresh OSA language instance with a fixed send handler. Every Apple event carries `kAEDoNotPromptForUserConsent`; macOS enforces current access on each event. Ordinary reads and writes no longer depend on the blocking Automation preflight API. Status sends a fixed application-version property event and requires an actual reply; it reads no note or account content. Only an explicitly approved OS-access request uses the prompting API. Content requests normally open the fixed Notes app in the background before launching the helper. Status does not launch Notes.

## Native repeat rules

`create_reminder` accepts `fields.recurrence` with an explicit due date.
