# HTTP setup for assistants

This technical guide applies to any compatible Streamable HTTP client. For the shorter owner-facing overview, see [Connect an HTTP-compatible assistant](../getting-started/http.md).

The optional Streamable HTTP transport lets a compatible MCP client connect to iCloud for Agents over HTTP. Stdio remains the default, and the ChatGPT private tunnel continues to use its existing connection. The HTTP server starts only when deliberately launched and listens on `127.0.0.1`, with an authenticated `/mcp` endpoint. It does not enable remote or public access on its own.

## Before connecting

Ask your assistant to review your existing installation and explain the client, the services and permissions that the HTTP instance will use. Approve each persistent client credential and the chosen remote connection separately. Keep your Apple credentials and HTTP client keys out of chat, URLs, logs and plaintext configuration. Your assistant should use a supported secure credential handoff; it must not claim a client is connected merely because it can discover the server.

Each client can be granted no access, read access or full supported access to each service. Managing other client credentials is a separate permission. The server enforces these permissions for every request, and its configured services, access modes, selected sources and existing approval safeguards remain the upper limit. Clients allowed to read the same service share that service's configured data scope; client keys do not currently restrict individual Mail folders or create separate data accounts. Supported Mail read-state changes, archive and Trash restoration use the same durable operation and recovery checks over HTTP and stdio.

A read-only Notes or Reminders client can ask for the macOS access needed to read its selected service. The owner reviews that exact request locally and handles any macOS prompt; this does not give the client permission to edit data. macOS may describe the underlying permission more broadly than the application's selected access.

The processes serving the same account must use the same private runtime directory and load the updated code for the shared operation locks to coordinate. An older process that is already running does not acquire the new lock. Plan and approve a coordinated restart of all affected clients and services before using them together; do not assume updating the files changed an existing process. Separate runtime directories do not share locks, approval records or recovery state.

## Client keys

Each HTTP client needs its own randomly generated bearer key stored in macOS Keychain, separately from the Apple app-specific password and the ChatGPT tunnel credential. Tell your assistant which client to connect, which services it may read or change, and whether it may manage other client credentials. The assistant can prepare the exact request with `http_prepare_client` and open the owner-review window. Nothing is activated until you approve that request locally, even when trusted-client approval is configured.

After approval, the assistant starts the action with `http_execute_client` and can check `http_client_status`. For creation, rotation or a separately approved handoff, the key appears in a local window for you to transfer directly into the client's secure credential field. It is not returned in tool results, printed, added to process arguments, stored in project settings or pasted into a conversation. Anyone with access to the screen can see it, and copying it places it on the clipboard. A client with a supported trusted launcher can instead receive its key through an owned anonymous pipe. Closing the window does not prove that the client saved the key or connected.

The key window selects the text for you. Press **Command-C**, paste it into the client's secure credential field, and close the key window when finished. You can also use its **Edit → Select All** and **Edit → Copy** menu items.

Keys are bound to the installation, its private runtime and effective service settings. A key cannot authenticate a differently configured instance. If those settings change, the assistant must prepare a newly approved permission update or replacement for the new configuration; it must not silently broaden existing client access. An old key can still be revoked from the same installation and runtime after a settings change. `http_clients` lists bounded client identities created through local review; continue its cursor even after an empty page. Keys created outside that workflow require their nonsecret client ID for management. A separately reviewed `authorize` action lets you handle any Keychain prompt and check noninteractive access for the server's Python identity. Changing the app or executable may require authorization again.

Ask your assistant to prepare a `rotate`, `revoke`, `show`, `permissions` or `authorize` action for the exact client. Each action needs its own local owner review. Rotation replaces that client's key; revocation disables that client without changing other keys. Permission changes apply on subsequent authenticated requests. These actions do not require an HTTP server restart, but already authorized work cannot be recalled. If Keychain is locked or access is unavailable, authentication fails until the owner resolves it. Secure delivery depends on the target client's actual credential interface; do not substitute a plaintext configuration file if the client lacks one. Existing keys without reviewed per-client permissions require an explicit permission review before they can authenticate.

An HTTP client without client-management permission can ask you to review changes to its own service access. It cannot change its client-management authority or manage another client's key. The requested change takes effect only after your local approval.

For Calendar, Notes and Reminders, a client with read access can also prepare one exact change for your local review without changing its ongoing permissions. Only that client can execute the approved proposal, and only once. The server's selected accounts and sources still apply. Other changes require the appropriate ongoing client and service permissions.

During creation or rotation, the pipe delivers a candidate before Keychain activation completes. The setup agent must wait for the successful lifecycle result before using it. If activation fails or its outcome is uncertain, do not assume the candidate works or repeat the action without checking the Keychain state first.

## Start and verify

An assistant with access to the installation can launch `scripts/run-http.py` using the installation's Python environment and validated local settings. The default port is 8765; the port can be selected explicitly. It should first check for an existing server, avoid disrupting it, and use only the approved service configuration. The endpoint is stateless: each request authenticates separately, and reconnecting clients establish their own connection without reusing another client's session. Start with read-only service access and verify the actual client can authenticate, discover tools and complete bounded reads for the selected services. An HTTP listener or successful discovery alone does not establish access to Apple data.

For an optional background connection, the assistant can use `scripts/manage-http.py`. It should inspect `--help`, use `--prepare` to preview the selected port, exact proxy hostname and whether the service should start at login, then review the result with the owner. After approval, `--configure` takes the returned `--review-sha256` and the same options; `--install` creates the service registration and `--start` starts it. The assistant can use `--status`, `--stop` and `--remove` to manage that separate service. These actions preserve existing client keys and other connections. Process status alone does not prove that the endpoint is reachable or that a client can read data. A changed installation or service configuration requires a fresh review.

## Remote HTTPS access

A hosted assistant needs an HTTPS address it can reach; `127.0.0.1` refers to the assistant's own environment, not your Mac. Choose an appropriate connection with your assistant. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) can serve devices authorized on a tailnet, but a hosted client must actually be able to reach that tailnet. A public HTTPS tunnel is another option and is reachable from the internet; anyone holding a client's bearer key can use that client's approved scope. Review the route, provider, credentials, data sharing, availability and any charges before enabling it.

The server remains bound to loopback. Configure its exact `--proxy-host` for the approved HTTPS hostname, retain the individual bearer key, and do not use forwarded identity headers as authorization. Keep the Mac and the chosen connection running when the client needs access. If the route stops, the client will not be able to reach the server. A connection provider can process traffic passing through its service; a model provider can receive the tool results requested by its client.

### Tailscale Serve

[Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) can proxy the local HTTP server to an HTTPS address available inside a tailnet. It is an external option for any compatible client that can actually connect to that tailnet; a hosted client is not automatically a member. This project does not install or configure Tailscale. A synthetic MCP read and access checks have passed over a private Serve route using the same Mac as the HTTPS client; reachability from another device or a hosted client depends on that client's tailnet access.

1. Check the installed Tailscale client, signed-in account, device name, access policy and existing Serve configuration. Confirm that the intended client can reach the tailnet and review the requested route with the owner. Do not overwrite existing routes or change tailnet policy as a setup shortcut.
2. Serve requires HTTPS certificates and MagicDNS. If enabling HTTPS is needed, explain that the device and tailnet DNS names appear in public certificate-transparency records, even though Serve access remains restricted to authorized tailnet devices. The owner handles any account or administrative prompts.
3. Start the approved loopback HTTP server, setting its proxy host to the exact Tailscale DNS hostname. After reviewing an unused HTTPS port and mount, a local assistant can configure Serve with the [current CLI](https://tailscale.com/docs/reference/tailscale-cli/serve), for example `tailscale serve --bg --https=<APPROVED_PORT> 127.0.0.1:<HTTP_PORT>`. Use actual reviewed ports, not placeholders. Port forwarding does not require root. Do not use `tailscale serve reset`, change an existing port's configuration, or use Funnel as a substitute for private Serve.
4. Inspect `tailscale serve status` and use its displayed HTTPS address with `/mcp`. Create the separately reviewed HTTP client key and have the owner enter it in the client's secure credential field. Verify discovery and an approved bounded read from the actual client; a running proxy alone does not verify access. Keep the server and Tailscale available.

Serve configured with `--bg` persists until disabled and can resume when Tailscale restarts. Before changing or removing it, inspect the exact configuration and use Tailscale's documented controls for that approved route. Disconnecting the proxy does not revoke the HTTP client key or erase information already shared with a client.

### Cloudflare Tunnel

A separately configured [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/get-started/) is one way to give an HTTPS-capable hosted client a stable address. Cloudflare's named, remotely managed tunnel requires a Cloudflare account and a domain on Cloudflare. Cloudflare's [Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) are temporary development connections; their changing addresses are not a durable client setup. Cloudflare is optional and is not a Python dependency of iCloud for Agents.

1. Have a local assistant inspect the existing installation, explain the public hostname and approved service permissions, and identify any account, domain or provider costs before making changes. Use a dedicated tunnel and hostname for this connection; preserve any existing ChatGPT tunnel and other services.
2. In Cloudflare's dashboard, the owner creates a remotely managed tunnel and a published application route to the selected loopback HTTP port. Use the exact HTTPS hostname and `/mcp` address for the client. Review the route and make sure the origin Host sent by Cloudflare matches the server's configured hostname or its loopback address. The route configuration is controlled by Cloudflare and can be changed there; the local launcher does not inspect or enforce Cloudflare dashboard settings.
3. Install an official `cloudflared` executable through a reviewed source. The local assistant verifies its publisher-provided checksum and records the executable's own SHA-256 and absolute, non-symlink path. The owner saves the tunnel token personally as a separate macOS Keychain password item: service `icloud-for-agents-cloudflare-tunnel`, account equal to the exact tunnel UUID. This token is separate from the iCloud for Agents client key and Apple password. Do not paste it into chat, command arguments or a project configuration file.
4. The local assistant checks `scripts/start-cloudflare-tunnel.py --help`, runs its nonsecret preflight with the reviewed executable path, SHA-256 and tunnel UUID, then starts it with `--start-with-keychain` after approval. The launcher reads only that Keychain item and passes the token to `cloudflared` in its process environment, not its arguments. Processes running as the same macOS user may be able to inspect that environment. The tunnel runs in the foreground; the owner can stop it, and a restart needs the same reviewed nonsecret details. The HTTP service's optional login setting does not start the tunnel. The owner handles any Keychain prompt.
5. Start the loopback HTTP server with the same validated installation settings and selected proxy hostname, using the background service above if desired. Prepare a separately reviewed client key, then have the owner enter that key in the client's secure credential field. Check authentication and tool discovery, then perform an owner-selected bounded read if the owner wants to share that data. A working public address or a saved connector alone is not proof of an Apple read.

The launcher verifies that the token names the reviewed tunnel and uses Cloudflare's default edge; tokens with a custom endpoint are not supported. The tunnel token permits operating the Cloudflare tunnel; the client key permits the selected iCloud for Agents access. Rotate or revoke each through its own service when appropriate. Stopping the local tunnel disconnects the route but does not delete either credential or erase information already sent to a client. Cloudflare's dashboard may offer a command containing the tunnel token: the owner should extract the token privately for Keychain rather than running or sharing that command.

For client-specific connection steps, see the [client guide](../getting-started/clients.md).
